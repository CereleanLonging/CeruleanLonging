# 302 产品派生 SQLite 索引

2026-10-23。沿用 [299 设计](SQLITE-DERIVED-INDEX-DESIGN-299.md)、[实施方案 v2](../../multi-agent-workbench-implementation-plan-v2.md)及旧 P1/301 证据。本项是产品查询缓存的实现差异，不重做模型接入，不代表正式验收或打包完成。实际测试状态以 [302 报告](../reports/sqlite-derived-index-302/summary.md) 为准。

## 已实现的边界

- 基础 `Store` 与每个 `DurableWorkflow` 各在自身数据根维护 `index.sqlite`。JSON 事件仍先验证、发布和重放，SQLite 不参与批准、派发、验收、资源释放或恢复判定。
- 索引包含 schema、账本类型、事件数量、链头和工作流绑定摘要；事件序号、类型、operationId、时间、哈希、任务/尝试；计划与批准状态、任务现态、跨日未完成任务、每日卷路径与阅读内容。没有接入凭证槽或模型私有推理数据。
- 缺失、损坏、schema/链头不一致、伪造超前、字段/内容改变时，从已核验内存重建。读取核对 SQLite 完整性、预期链头和由权威事件算出的内容摘要，失败回退已核验内存。当前产品快照与日报查询已使用缓存；`unfinished_before` 提供跨日阅读查询，调度仍直接读取领域状态。
- 在私有临时文件使用 MEMORY rollback journal 和短事务，关闭 SQLite、同步文件后发布。正式路径不使用 WAL，不保留 SQLite 连接。目录伪装、reparse/junction、硬链接会拒绝访问；未知 journal/WAL/SHM 保留并降级，不擅自清理或恢复外部 SQLite 状态。
- 已提交事件之后的缓存失败不会改变原命令成功状态，不重复派发；原 `state.json`/日报投影失败仍遵循必须重开的旧规则。基础工作区概览能提示索引降级；底层两账本也暴露独立 `index_error` 诊断。
- `inspect_existing` 保持严格只读，不创建/修复缓存。旧账本的跨日日期沿用固定 UTC+8；新时区账本沿用已有命名时区规则。复用已计算日报，避免一次命令重复渲染。

## 依赖及发布

已通过正常宿主网络审批取得并锁定 `rusqlite =0.40.2`（关闭默认特性，仅启用 `bundled`）与 `libsqlite3-sys 0.38.2`，后者静态编译 SQLite 3.53.2。另新增 `fallible-iterator 0.3.0`、`fallible-streaming-iterator 0.1.9`。与本轮修改前锁文件比较，没有删除或升级原有包；仅 core 新增直接依赖。未修改持久代理、信任、证书或签名密钥。299/301 的“依赖不可得”现为历史结论。

原始许可证及锁文件校验和保存在 `reports/sqlite-derived-index-302`。新包还需纳入许可证文件并核对原生载荷；现有 297 / 0.1.20 / reader16 冻结候选未改，不能用它证明本能力已交付。
