# 持久化工作流与每日交接 v1

更新：2026-10-07。实现为 `crates/core/src/scheduler.rs` 和 `handoff.rs`。已完成库级迁移及进程故障测试，尚未连接桌面调度入口、真实适配器和常驻服务。

## 账本与提交顺序

`DurableWorkflow::open` 接收可信宿主提供的 `SchedulerConfig`，核对 schemaVersion=1、core 绑定和完整身份表。首建写入 bindings.json，后续必须完全匹配。`writer.lock` 使用操作系统文件锁，进程退出后释放。

每条事件包含 schemaVersion、operationId、receivedAt、bindingsDigest、领域事件、上下文、previousHash 和当前 SHA-256。启动按文件名排序，核对连续序号、文件名、重复操作 ID、哈希链、身份表摘要、时间单调性以及每一次领域转换。遇到损坏拒绝打开，不跳过坏 JSON。残留 `.tmp` 不视为已提交事件。

提交顺序：验证身份与状态 → 验证上下文 → 计算后续状态及可生成的日报 → 写同目录独占临时文件并 sync_all → rename 发布事件 → 写日报与 state.json → 返回成功。派发或取消的外部动作必须等一次全新的意图成功返回后才发生。写入开始后出现错误，实例禁止继续命令，必须重新打开并对账。

相同操作 ID、身份、内容与上下文的普通命令可返回原事件。派发/取消意图的重复 ID 一律拒绝，即使调用方未设置 require_new；换一个 ID 也不能绕过状态检查。恢复对 dispatching/running/cancelling 追加持久化 unknown，保留资源。恢复事件 ID 若与已有操作重名，使用未占用的后缀，不因名称碰撞阻止重开。

## 上下文与身份边界

- 批准必须带 approvalSource。
- 派发意图带 threadId 与 cwd。
- started、submit、cancel-intent 必须匹配派发会话并携带 turnId。
- submit 还需匹配已记录的轮次，terminalStatus=completed。
- 取消需 cancellationSource，并核对已记录轮次。

这些字段是可信宿主声明，不是已经完成的认证系统。回执对账目前仍由可信宿主核验后以 evidence 字符串提交；产品需补结构化回执、证据哈希、策略版本及权限通道。不得把本库的 principal 参数直接开放给前端或 worker。

## 每日文档

`project_handoffs` 是纯投影。输入必须来自已验证事件；按接收序号去重与排序，重复冲突、断序和接收时间倒退均拒绝。沿用 Asia/Shanghai 固定 +08:00、30 个新任务或 256 KiB 的原型默认值。任务后续更新不消耗新任务额度，封卷后更新写当前卷并标注初始卷。跨日携带未完成项，submitted/blocked 仍未完成；迟到事件按接收日归档并显示发生时间。文本转义为普通 Markdown 文本。

路径：`daily/YYYY-MM-DD/handoff_YYYY-MM-DD_NNN_HHmmss+0800.md`。state.json 包含卷索引和最后账本摘要。日常追加不改写内容相同的旧卷；投影被误改或丢失时可从账本重建。日报内容不提供批准、执行或状态真相。大块证据应保存为产物引用，单条投影超出容量会在事件提交前被拒绝。

宿主将工作流任务事件映射为日报：propose/approve 留在权威账本，不生成任务日报条目；日报序号连续，messageId=`event-<账本序号>`。unknown 显示 blocked，并附“对账后继续，禁止自动重发”。当前 receivedAt 与 occurredAt 均来自账本接收时间，时间精度归一到毫秒；没有伪造独立供应商发生时间。

严格日历校验比 JS 原型更收紧：拒绝 2 月 30 日、闰秒和超过三位小数的时间戳。有效输入的 18 组固定夹具中，10 组完整卷结构与字节输出一致，8 组均拒绝。原型来源和 SHA-256 保存在 `tests/fixtures/handoff-parity-v1.json`，普通测试不重新生成基线。

## 验证范围

| 场景 | 实际检查 | 结论范围 |
| --- | --- | --- |
| 四个落盘点退出 | 写前、临时文件同步后、事件发布后、投影后；独立子进程退出并重开 | 未发布不当作提交；已发布恢复为 unknown；单一派发意图 |
| 三个派发点退出 | 发送前、副作用后 ACK 前、ACK 后；外部测试 worker 独立存活 | 观测发送/文件副作用分别为 0/0、1/1、1/1，恢复不重发 |
| 对账 | 发送前结合存活路由计数；已完成核对实际 receipt 文件 | 不只因文件缺失就推断未发送；submitted 仍待独立验证 |
| 投影故障 | state.json 被目录占用，写入报错后重开 | 已提交意图保留，原实例不能继续派发 |
| 文档重建 | 改写 Markdown 和 state.json 后重开 | 恢复原文，事件数不增加，不执行文档指令 |
| 分卷 | 31 个真实调度任务加旧任务更新 | 生成两卷，第一卷内容及文件修改时间不变 |
| 内容膨胀 | 原事件大小合规、转义后超卷容量 | 提交前拒绝，账本/状态不变，仍可处理下一条合法命令 |

崩溃夹具使用真实进程和真实文件副作用，worker 是合成执行器，模型调用数为 0。它不能替代供应商 ACK 丢失、真实 CLI 取消或第三方桌面恢复验收。首次进程测试因 Rust 测试框架输出前缀与测试消息粘连超时；已修复消息换行并全量复测，原失败日志保留。

## 剩余门槛

1. 常驻命名管道服务、当前用户 ACL、可信角色入口、CLI 和 UI 共用调度核心；现有桌面仍用基础 stdio Store。
2. SQLite 可重建索引、配置化时区、检查点和大账本性能。当前每次提交重放并生成视图，为正确性基线；大规模性能尚无结论。
3. 磁盘满、共享文件占用、备份/迁移、真实强杀和物理断电专项。当前 sync/rename 与进程退出结果不等同断电保证。
4. 权威账本不是同用户恶意篡改的防护边界：无外部可信锚时，完整重写链或删除尾部不能由哈希链单独证明。路径/文件锁校验也不是 OS 沙箱。
5. 日报投影目前同步提交，失败会停止该实例；后续可在可靠队列和观测机制下异步生成。额外手工创建的无关日报文件不读取也不自动删除。

以上缺口继续阻止 P1 整体通过；P2–P6 继续按主实施方案逐项验收。
