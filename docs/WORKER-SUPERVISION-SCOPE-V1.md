# 按执行配置设置异常监督

日期：2026-10-13。本文描述当前源码契约；构建、签名及实际验收范围以最新交接和对应报告为准，不能据此认定冻结的 0.1.8 安装包已经包含本次修改。

## 用户行为

项目默认监督策略继续控制默认执行器。每个额外执行配置可以选择“沿用项目默认”“关闭此配置的监督”或“单独设置 Codex 监督”。例如，项目使用受监督的 Codex 编程任务，同时给 API 或 OMP 配置明确关闭监督，便可保留 Codex 的监督策略。添加或修改其他执行配置不会清空项目默认策略。

监督仍依据观察到的同一命令连续失败，阈值为 2–8 次；每次尝试建议额度为 0–2 条。额度为 0 只记录异常，不请求建议；额度非零且未批准发送时可以保存建议，交由用户审阅。勾选发送后才允许把建议送到原 Codex 执行轮次。它不推断所有卡顿或循环，也不授权副指挥直接修改业务文件。

运行中主动监督目前仅支持 Codex。API、OMP、Qoder 或 WorkBuddy 配置若继承了已开启的策略，界面明确显示冲突并阻止保存，核心也会拒绝。用户可以明确关闭这些配置的监督；系统不通过静默丢弃策略来消除冲突。

## 配置与批准

`WorkerProfileDraft`、保存的 `WorkerProfile` 和方案中的 `TaskExecution` 增加可选 `supervisionOverride`：

| 值 | 效果 |
| --- | --- |
| 缺省或 `null` | 沿用项目默认，包括原有的执行器支持限制 |
| `{"mode":"disabled"}` | 此配置关闭监督 |
| `{"mode":"enabled","policy":{...}}` | 此配置使用完整的独立策略，仅支持 Codex |

缺省字段在序列化时省略，原配置与方案不会因新增字段自动改变摘要或获得权限。显式关闭与缺省继承是不同的批准内容，不能互换。配置更改须重新规划、展示各任务最终策略并由用户批准；原批准不自动跟随新设置。

这里的兼容性是当前实现读取旧数据。旧版的严格解析器会拒绝包含新覆盖字段的记录，不能据“旧摘要保持”声称可以无损降级读取新数据。本批尚未发布新的安装包；后续发行前须同步版本、数据写入者与最低读取能力门禁，并验证备份和回退边界。不得用冻结的 0.1.8 安装版直接打开这批新记录来证明兼容。

执行配置的可选监督覆盖字段在任务物化时复制到 `TaskExecution`；最终策略由原方案默认策略与该任务覆盖共同解析。核心根据原任务、原方案及原执行配置解析最终策略；启动、建议请求、投送和恢复都使用同一语义。无法对应到原批准任务、配置内容不一致或不支持的执行器策略均拒绝，不回退到另一个配置。
