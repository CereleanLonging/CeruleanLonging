# OMP 文件还原核心 V1

后续更新：产品用户IPC与复核界面已接入，见 [文件复核与还原界面](OMP-FILE-RESTORE-UI-V1.md)。以下保留核心阶段的验证边界。

2026-10-10。承接 [写入前像与恢复核查](OMP-WRITE-EVIDENCE-V1.md)。核心现已实现复核后的原文还原、恢复原先不存在状态，以及还原自身的持久记录和只读核查。该接口尚未接入产品用户IPC或界面，也未向模型工具目录开放。

## 准入与复核

`restore::review` 从当前 DurableWorkflow 派生原计划、批准、尝试、完整 DispatchIntent，要求当前任务为原尝试的 Unknown，且历史中有对应 DispatchIntent。原 prompt journal 必须存在并已派发；未派发或 Completed 终态拒绝。没有终态、Error、Aborted 可以在任务仍为Unknown时复核。

同时取得原 prompt journal 和工具journal的独占锁，并核查写入前像、原工具参数和当前文件。返回 RestoreReview，绑定计划/尝试摘要、工作流末条哈希、prompt和工具journal头，以及当前文件SHA和前像摘要。

`restore_original` 要求调用方传入来自本地用户命令通道的身份，身份必须在项目配置中具有User角色，原批准包含WriteFiles。它重新派生完整复核记录并逐字段比较；任何变化都会使旧决定失效。随后锁住实际目标文件，再次比较当前SHA，避免复核与执行之间用户改动被覆盖。

这里的用户身份是受信宿主接口参数；真正的IPC身份来源、展示复核内容和用户点击还原仍需后续产品集成。测试中的User身份是离线夹具，不代表已完成原生用户流程验收。

## 一次还原的执行

在 `service_root/repairs/<SHA256(callId)>/` 新建独占记录目录。每个原工具调用只允许首次还原；目录已经存在时拒绝再次执行，包括上次中断的情况。

先保存并同步current.bin（用户本次复核时的内容，若存在）、original.bin（原写入前内容，若存在）和decision.json。decision绑定整个复核记录、用户和时间，全部准备成功后才修改项目。

原先存在文件时，独占句柄内写回原字节、调整长度、sync_all；当前文件丢失则使用create_new重建，拒绝覆盖复核后出现的新文件。原先不存在时，通过已校验且独占的文件句柄设置Windows删除标记，关闭句柄后确认文件不存在；不按未经固定的路径删除。

操作后重新观察目标SHA或缺失状态，符合原状态后才保存result.json，绑定review摘要、用户、恢复SHA和时间。该结果只说明这次文件还原，原工具事件、工作流历史和Unknown任务状态均不改变，不会重新派发或验收原任务。

## 还原核查

`inspect_restore` 持有原证据锁，校验decision、两份内容、结果绑定和当前文件，报告是否有result记录、当前SHA是否仍等于原文件。历史还原成功后用户再编辑文件时，仍保留历史result，同时报告当前不再等于原文件。

当前核查入口仍要求原未知尝试和相同证据/工作流头；任务后续变迁后的历史展示还需与产品历史系统接入。中断还原保留原复核内容和目标原文，仅核查，不自动重放。新的补救决定/多次补救链尚待实现。

## 验证

新增六组测试：还原原文/原不存在状态、保持Unknown且不能重复、缺失目标重建、陈旧复核/错误角色/缺失前像拒绝、回执绑定破坏拒绝、非Unknown或Completed原调用拒绝，Error/Aborted原调用在Unknown下可处理。

实际进程终止矩阵覆盖两类还原（写回原文、删除本次新增文件）×prepared、partial、mutated、recorded四个位置，共八个位置。重开原工作流和证据后，原任务仍Unknown；操作前内容及原文保留；缺失result不被补成成功；再次调用拒绝。删除标记在进程终止导致句柄关闭时生效，因此删除分支partial处文件可已消失，仍没有成功回执。

测试只操作隔离临时目录并终止自己创建的子进程。目录随测试清理，保留源码选择集和日志。首编译发现Windows绑定DeleteFile字段为bool，修正后通过，失败日志保留。
