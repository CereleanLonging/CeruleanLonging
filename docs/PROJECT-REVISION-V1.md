## 产品流程

已批准方案全部任务为 Pending、Accepted 或 Cancelled，且无活动执行器、未知执行/验收和未决指挥请求时，方案卡片显示“修订下一版方案”。用户审阅收口/取消/尚未开始数量并填写原因；界面说明确认后未开始任务也停止旧方案后续派发。返回不修改状态，提交核对当时方案、工作流链头、运行记录和配置的证据摘要。

核心先持久化暂停旧运行，再记录受信用户 RequestRevision，最后将旧暂停运行记为 Superseded（已转入修订）。这不是业务验收通过，原 Cancelled 不会变成 Accepted，原 Pending 不伪造为执行后取消。已经 Completed 的历史运行保持原状态。

用户随后修改并保存需求/工具/预算配置，请求主指挥生成下一版。版本必须递增，旧批准不适用于新方案。新方案需重新审阅批准，并明确启动项目才可执行；请求修订、保存配置、生成方案和批准本身都不自动启动 worker。累计主副指挥请求数不会因修订清零。

## 历史与恢复

保留原始工作流和运行记录。原 attempt ID 永久占用；显式修订后的相同任务 fence 根据历史分配次数继续递增，包括移除后重新加入的任务。旧协议未出现 RequestRevision 时仍按原规则回放，新增可选状态字段缺省不改变旧序列化内容。

原批准、提交、Verify、Accept 及详情仍关联原版本，而不是套用最新方案。所有待修订旧方案动作被拒绝。Superseded 不可恢复/暂停，不占用下一版的唯一未完成运行名额；该状态必须有原版本范围内真实的用户修订事件，不能仅改运行状态文件放行。

在工作流事件发布前失败，已成功保存的暂停仍保留，恢复存储后可以重新审阅提交。在工作流事件已提交、运行结束记录尚未发布的窗口，重开先校验所有工作流/管理/运行证据，再从真实 RequestRevision 补齐旧运行状态，且仅补一次；不会创建批准、模型请求或任务。测试覆盖文件路径故障导致发布无法开始，未据此放行任意磁盘损坏或残留 `.pending` 的自动修复。
