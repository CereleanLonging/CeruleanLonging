## 已发现的问题

当前源码会持久保存新的 `supervisionOverride`。旧版严格解析器无法读取，但现有数据标记与更新检查尚未表达这一能力变化。因此不能仅把产品版本从 0.1.8 升为新 patch 就认定旧版可以回滚读取新数据。

`None` 仍不写入字段，旧字节和摘要保持；显式关闭与显式开启都会写入新字段，都需要保护。本轮只使用隔离夹具，没有发行新包或升级用户数据。

依据：`crates/core/src/data_format.rs`、`project_setup.rs`、`main.rs`、`backup.rs`、`lib.rs`，以及 `scripts/manage-windows-update.ps1`。现有备份会固定原文件，发布使用禁止覆盖操作；直接覆写旧 `00000000.json` 不符合既有不可改写和共享锁约束。

## 最小改造方向

1. 在配置保存及方案持久应用入口检查读取能力，早于配置 pending、管理应用记录和工作流事件写入；不能只限制界面。未受有效代际保护的目录拒绝写入两类新覆盖。已有新字段却缺保护时要求核查，不自动补造历史证明。
2. 复用停核心、原 hold、冷备份、摘要绑定审阅与明确发布。新增不可变读取代际保护文件，避免改写旧 schema 2 marker。新核心先验证保护再加载配置和事件；旧核心须把保护作为未知内容拒绝，并在构造执行宿主前停止。保护文件的具体位置和命名必须以冻结旧核心实测拒绝为依据。
3. 区分容器 schema、保护格式和有效最低读取代际。`data-format status` 返回有效代际，新核心 build-info 声明自身读取代际；更新需同时满足 schema 和代际条件，并把该能力纳入实际输出与清单比较。旧包缺字段只按明确的旧版本映射处理，不把任意缺失值视为兼容。
4. 新格式事务需阻止旧维护控制器接管；评估最小提升程序更新协议与事务 schema。旧事务仍由原控制器处置，不改写冻结历史。数据代际提升放在程序更新事务完成之后，避免破坏进行中的原数据一致性核查。
5. 提升前继承原二进制回滚条件；提升后拒绝直接回退到旧 reader。需要回退时，先由支持该备份 writer 的维护核心恢复经审阅的旧代际备份，再核对旧核心能力。不通过删除保护文件或新字段伪造兼容，不自动重放备份后的任务。
6. 制作新候选时同步唯一新版本、备份 writer 白名单、build-info、能力清单和实际 runtime 摘要。旧白名单继续保留，冻结 0.1.8 及更早包不改写。新版生成的旧代际备份也可能被旧核心按 writer 拒绝，不能省略这层检查。
