## 目前能证明的内容

`scripts/money-readiness-289.py` 只读取 286 的 `latest.json`、管理/执行摘要和六份原始回执，逐份重算 SHA-256，对照请求数、用途、操作 ID、响应 ID、实际模型和 token 用量。这证明当前本地文件之间的一致性，不认证供应商账单或防范同一主体同时改写所有本地材料。输出仅包含必要的身份、计数及摘要，不复制提示词或原始回复。结果保存在 `reports/money-readiness-289/latest.json`。它不是账单导入器、价格计算器或发送许可。

286 的 3 次管理请求和 3 轮执行请求均有唯一响应 ID，合计输入 43,735、输出 951 tokens。仅 2 份回执报告缓存读取，共 9,088 tokens；另外 4 份没有该字段。6 份均没有缓存写入字段。`reportedSum=0` 只表示已报告值之和，**不等于未知字段的实际值为零**。原 `actualMoney=null`，本轮继续为 `null`。真实编程已通过，不代表对应费用已核销。284 的传输未知及其他历史调用不在这六笔之内，也不能因此记零或遗漏。

当前 `ApiUsage::billable_usage` 明确拒绝 A6API；`Host::require_currency_execution_available` 仍拒绝金额预算执行。现有 scoped 报价合同限定官方 OpenAI 端点，不能把其身份、缓存语义或默认服务档位移植到 A6API。用户允许中转调用不等于审阅了某份报价，也不证明中转支持金额上界。

## 需要冻结的 A6API 报价合同

在考虑生产金额预算前，应由真实提供方条款形成**独立 A6API 报价身份**，经用户审阅并按摘要绑定到项目批准版本。至少包含以下字段，缺任一影响金额的字段就维持未知：

| 维度 | 必须明确的内容 |
| --- | --- |
| 供应商与账户 | A6API 的账户/计费主体、端点 `https://api.a6api.com/v1/chat/completions`、准确请求模型 `gpt-6.1-sol`、可能返回的实际模型集合；不能写作 OpenAI 官方账单。 |
| 时效与来源 | 条款版本、来源、有效起止时间、记录摘要、用户批准摘要；执行及结算均绑定原报价，不用后来网页价格重算旧调用。 |
| 费用单位 | 原始结算币种/余额单位、输入/输出/缓存读写价格、每次请求或会话/阶梯计费方式、上下文长度与服务档位条件、最小收费和舍入规则；跨币种换算需另行批准有时效的汇率，不能默认 USD。 |
| token 语义 | `prompt_tokens` 是否已包含缓存命中/写入，缺失的缓存字段如何解释，缓存费率是否另计；按所见 Chat Completions 形状逐字段确认。不能把 `null` 转成 0。 |
| 请求边界 | 生成前完整输入的可验证上界，输出上限、工具和历史消息的计数范围、可能的路由/模型/档位变化，以及超限时供应商的经济保证。只有输出 `max_tokens` 不足以限制整次费用。 |
| 附加项目 | 调用/计数请求费用、税费、服务费、优惠、退款、最低消费和套餐抵扣的处理；这些不能从公开每百万 token 标价推断。 |

报价供**未来请求预留**；它不是 286 的实际账单。若提供方不承诺请求前的可信上界，不能仅靠本地估算解除 Host 金额门禁。任何金额算法应继续使用整数和一次请求一次舍入，并复用现有项目金额单写账本，避免另建余额。

## 账单对账证据及状态规则

每笔账单需有提供方导出的不可变交易/请求身份、账户、时间、币种、原金额与调整、原来源摘要，以及可核实的响应 ID 或明确的一对一关联证据。先核来源、范围与唯一性，再对 286 六个响应 ID 逐笔匹配；重复、冲突、跨账户或无法关联的记录不能自动归因。只有合计余额而没有逐笔关联时，可记录账户总额，**不能**据此给六次请求分摊“实际费用”。明确的零元账单也必须有提供方证据，不能由字段缺失推出。

对 284 等“发送可能发生、未获回执”的尝试，先从原调用库存收集身份与时间窗口，再用提供方账单/请求日志核销；无匹配不等于未计费。对账必须覆盖本项目及同账户历史相关尝试，不能只因 286 成功便释放旧未知责任。账单核销与本地执行退役分开，保留原账本 head 和来源引用。不可见的税费/余额调整应作为单独未分配责任，不挤入已匹配请求。

建议状态为 `未取得账单`、`有账单但关联不足`、`金额冲突待审`、`逐笔核对已完成`。只有最后一种可展示实际归因金额；即使完成历史核销，生产执行仍须另过报价、授权、预留、回执、恢复和经济边界检查。当前状态为**未取得账单**，六笔均待匹配，`actualMoney=null`。

## 下一步可执行顺序

1. 在用户自己的 A6API 后台取得实际条款和交易/用量导出，优先保留原文件及 SHA-256；不要把 Key、完整账户号码或含敏感内容的导出粘贴到聊天。若导出无法关联响应 ID，先确认提供方是否有请求级查询或可导出的账单关联字段。
2. 在新隔离材料中审阅 A6API 的价格、缓存/路由及币种语义，冻结原始报价和账单映射合同；不将官方 OpenAI 报价或公开目录价格当成 A6API 事实。先对 286 六笔只读核销，并把 284 未知尝试纳入同账户未分配责任检查。
3. 仅在报价和请求前可信上界成立后，设计 A6API 专属的计数、预留、单次发送、结果费用 ACK、未知恢复及账单核销差异；复用现有金额单写账本。待这些和真实故障场景通过，再考虑是否解除相应 Host 金额门禁。此阶段没有执行该解门禁动作。

289 是只读证据前置，不计作 P3-MONEY 正式验收，也不是 245 真实效率样本；正式产品仍未全部签收。
