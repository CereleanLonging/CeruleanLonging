## 第一项交付：把已有多检查验收带入产品流程

先让一个项目明确配置两项或更多有序检查，例如“语法检查 → 单元测试”，每项都有稳定 ID、用户可读名称、已登记 validator、显式参数和时限。检查均为必需项；第一批不增加“允许跳过失败”“模型自行生成命令”或任意 shell 字符串入口。执行顺序、参数、工具文件摘要和总时限都进入待批准方案。

需要改动的集中位置：

1. `domain/project_setup.rs`：增加有版本的有序检查配置。逐项校验已登记工具、唯一 ID、数量与参数上限，限制检查时限和总验收时限；模型只能引用用户已经选定的工具配置。
2. `core/project_setup.rs`、`project_planning.rs`：保存和加载新格式；将完整检查列表物化进各任务的 `TaskExecution.checks`。保持现有单项配置的显式兼容，不静默重算旧 SavedProjectSetup、PlanRevision 或批准摘要。旧数据可读取，改为新配置须形成新版本并重新批准。
3. `project_runner.rs::run_scope`：核对完整已批准列表，移除“必须恰好等于一个 setup.check”的产品限制，但不放宽实际工具与参数一致性。
4. `ProjectPlanning.tsx` 与批准界面：让用户增删和排序检查，在批准时完整展示；填写配置仍不产生执行授权。
5. 增加只读验收详情，返回原 operation、task、attempt、方案摘要、受测产物/副本摘要，以及每项检查的状态、退出码、超时和日志引用。界面区分“通过”“失败”“未运行”“结果待对账”，不能因为已保存一项绿色结果就将整体标绿。

沿用当前验收语义：普通非零退出码作为失败观察记录；后续能否继续由既有执行与时限逻辑决定，不在本批顺便更改为隐式重跑。超时、取消、进程失败或存储异常可能导致后续检查没有结果，应展示为未运行或未知。所有必需检查完整通过且产物仍未变化，才允许 Verify passed 和 chief Accept。

验收工具可能有副作用，不能因为某阶段已失败就自动新建 verification operation、重跑整个列表或从中间恢复。沿用当前意图、结果文件、未知验收处置与禁止自动重跑规则。受测副本和产物在各检查之间继续校验；不能把前一阶段修改过的输入当作原批准快照。

这项交付同时用两任务串行 DAG 验证多阶段收口：A 完成其全部检查并被 chief 接受后，B 才能开始；B 的检查与产物绑定它自己的 attempt。最小样例可沿用项目级统一检查列表，不把它称为已经支持任意按任务配置不同验收器。后续的任务级检查配置、并行工作区和最终集成快照仍保留为原路线工作。

## 第二项交付：明确监督事件、额度和停止原因

监督先记录核心能证明的事件，再请求副指挥。建议第一批支持三类：已知工具失败的相同分类重复、明确执行时限/无可观察进度超限、执行者的结构化求助。不能把“没有文本”“文件大小未变”或一次观测超时单独判定为循环。重复操作且无新产物的自动判断，需要受支持的工具事件和可靠产物进度证据，证据不足时显示待核对。

在 adapter 中仅提取白名单元数据：绑定的 thread/turn、事件种类、工具名称或分类摘要、退出状态、接收时间和有限长度的脱敏说明。排除私有推理、凭证、环境变量全集和任意工具原始输出。保留现有单一 transport 读者，不用第二个线程竞争读取 stdout。观测通道有容量、序号和丢失标记；存在丢失时不得声称完整重复次数已被证明。

建议新增小型监督记录模块，保存以下关联：

```text
incidentId / projectId / taskId / attemptId / threadId / turnId
revisionDigest / workflowSequence / observationSequence
triggerKind / evidenceDigests / status / adviceCount
managementOperation / deliveryOperation / escalationReason
```

字段名是待定契约，不代表当前已存在。incident 以同一已绑定事件去重，不能每次轮询生成新的计费请求。上下文保存行动摘要和证据引用，原始日志仍有大小限制；文件交接只是该记录的可读投影。

原实施方案建议“同类失败 2 次触发、每轮最多 2 条建议”。本批可采用其作为新配置初值，但必须进入实际批准的监督策略，不能默默给旧批准增加自动纠偏权限。建议同时绑定每 attempt 的建议次数、总管理请求数和截止时限；新的 incident、重启、刷新界面不能重置同一 attempt 的计数。费用未知仍显示不可精确测量。

必须区分“监督异常需处理”和“用户主动暂停/停止”。可在持久运行控制中增加明确原因/来源，或复用可证明的用户控制事件序号；不能通过中文 message 字符串判断授权。用户暂停、已请求停止、Cancelling、Cancelled、Unknown 或原控制所有权丢失时，一律禁止自动发起管理调用或送达纠偏。必要的只读对账与已有执行结果收集继续进行。

## 第三项交付：从建议落账到一次受控送达

本批先保留严格角色分工：副指挥只输出建议及依据，不给 shell 命令执行权限，不修改批准目标，不代替 worker 提交产物。权限或预算不足、需要扩大范围、超过两条建议、建议过期，均升级主指挥/用户；不以“继续目标”为理由自动创建新任务或新 attempt。

采用现有管理请求的持久化模式，并为活动监督增加窄入口：

1. 唯一 worker 在活动 Running 边界产生受控监督快照，绑定原 attempt、thread、turn、方案、工作流位置和最新观测序号。Host 使用该快照与 incident 组建管理上下文，先保存请求意图，再调用一次 OpenAI 副指挥。
2. 该入口只允许 `Purpose::Advise`，并核对运行授权和监督额度。不要对所有管理操作绕过 `require_available`；通用 Plan/Assign/Accept 和验收继续遵守现有互斥。
3. 回答绑定原 stateDigest 与 incident。将“建议已保存”“建议已入队”“已向执行器送达”“送达结果未知”分别记录；管理 `.3` 或本地 Advise 事件不能冒充远端送达成功。
4. Host 与 worker 的握手可沿用已有分配准备/提交回执结构：Host 持久管理应用意图，唯一 worker 重新核对当前状态并保存本地 Advise 关联，Host 保存对应回执。处理由同一建议自身引起的状态推进时，核对精确已提交事件，不全局放宽过期检查。
5. 只有安装的 Codex 版本存在已核验的在途纠偏协议和可核对回执，才启用实际 steer。实现前读取本机版本/协议 schema；不凭方法名推测参数、幂等性或成功语义。建立绑定原 turn 和建议摘要的持久送达意图后，由持有同一 transport 的 worker 发送至多一次。
6. 已自然完成、取消开始、用户暂停、预算耗尽或观测版本不再匹配时，拒绝送达并保留建议供审阅；不会为了让建议“生效”开启第二轮任务。发送结果不确定时登记 Unknown，不重发；只有官方可用的只读证据可以确认原送达结果。

若当前协议不能证明有界、可关联的 steer，仍完成事件和建议链并展示“已记录建议，尚未送达”，将实际送达能力保持未验证；这只是分阶段工程成果，不算完成用户要求的自动纠偏。不能把向其他聊天发消息或重新执行 `turn/start` 作为替代。

控制通道需要同时处理取消与建议。取消优先，已接受的停止请求使队列中尚未发送的建议失效；不得截断已经开始的协议帧。复用本轮取消的半帧缓冲与审批拒绝完整发送保证，由唯一所有者串行操作 transport。若平台调用不支持中途撤回，记录已开始的动作及随后取消，不能伪造“从未送达”。

## 执行顺序与放行范围

第一步冻结最小多检查配置和兼容策略，完成 M1–M7 与 U1 中的验收部分。第二步实现事件、incident、已批准监督策略和本地建议链，先以模拟副指挥证明 S1–S5。第三步在实际安装协议核验后实现唯一 worker 的 steer 通道，补齐 S6–S7 和原生完整链。每步沿用 fmt、clippy、Rust/Node 回归、TS 契约与桌面构建；涉及控制权变更时重跑活动取消回归。

无真实 Key 时，上述独立工程可以继续；模拟管理输出只能证明事务与权限，不能证明真实主副指挥身份、建议质量或真实计费预算。真实 Key 配置后，另验“真实用户批准 → 真实副指挥建议 → 原任务纠偏 → 独立多检查 → chief 收口”，并保留失败样本。真实 Codex steer 需要单独的小任务证据，不能由取消测试或合成协议回归代替。

用户暂停或停止后的项目不会因这些测试或功能自动恢复。Cancelled 任务只能在用户修订、重新批准并明确恢复后的新授权中开展后续工作；下一批工程与验证夹具不应自动为取消的用户任务创建后继任务。
