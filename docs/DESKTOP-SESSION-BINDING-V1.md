# 已有桌面会话观察与用户关联 V1

2026-10-10，第036项建立关联，第037项补固定消息验证。接续原型 Qoder / WorkBuddy 的既有会话路线，新增产品接入管理入口。这里的“关联”是用户确认保存的一次观察，不是桌面派发授权。产品现在可另行审阅并确认 Qoder 0.4.3.0 的一条固定纯文本验证消息；这不授权编程任务。桌面任务派发、取消和自动接管仍属于后续 P4 工作。

## 产品流程

接入管理 → 发现已打开窗口 → 选择具体窗口 → 读取当前会话 → 审阅项目关联 → 选择已登记项目、填写名称并确认 → 后台再次观察 → 保存关联。

发现结果保留各个窗口，不因同标题而自动选中。身份包括程序路径、产品版本、PID、进程启动时间和 HWND。核心只接受刚发现的窗口；观察摘要由核心生成，用户命令不能上传伪造的聊天观察。确认前的观察超过120秒会被拒绝；保存前再次读取，窗口身份、会话ID、文档runtime ID、内容与布局指纹、节点数量、草稿与忙碌状态必须一致。

关联项目由用户指定，外部应用真实工作目录与工具权限仍须用户核对。第038项增加Qoder模型按钮显示名观察，不能当作供应商模型认证；WorkBuddy模型识别尚未适配。每次重开只显示历史关联，清空当时的窗口列表和可批准观察，不自动认定旧 HWND 或 runtime ID 仍然有效。用户关闭程序、改变聊天或应用升级后需重新核对，不能据旧关联直接执行。

## 两种身份证据

Qoder 从其 UIA Document 路由提取聊天 UUID，保留该 UUID 与原窗口、指纹共同核对；不保存完整路由。它是应用界面提供的标识，不是供应商认证凭据。

WorkBuddy 不生成伪造的供应商会话ID。当前只保存用户选择、窗口身份和可见内容指纹，UI明确说明其限制。内容相同的不同聊天、历史虚拟化/裁剪、动态界面变化仍不能靠一个指纹完全区分；这也是当前没有开放桌面任务发送的原因之一。后续必须结合用户确认的历史连续性锚点与动作前复核，逐版本验证。第037项仍不开放 WorkBuddy 发送。

## 观察器与边界

Rust 核心编译时用 Windows .NET Framework 4.x 的 x64 C# 编译器生成固定观察器，并嵌入核心文件。运行时只提取嵌入的同一内容，核验全部字节并持有禁止写入/删除的文件读取句柄，再通过既有 Windows Job 运行。生产侧不接受外部观察器路径或任意操作名称。

桥接的 discover / inspect / trialprepare / trialread 不输入文字或发送；trialsend 才能输入并 Invoke 一次固定消息。没有面向用户IPC的任意文字、鼠标点击、取消或键盘快捷键接口。第039项增加受信任核心调用的批准任务发送/回读底层，尚未在产品UI或持续调度中开放。每次一个后台进程，读取20秒、发送及回读最多90秒，有界输出及进程树清理；读不完整、页面不唯一、草稿不空、忙碌或批准控件出现时拒绝产生关联观察。发现最多32个窗口，观察最多1000个节点；树查询本身可能被 UIA 阻塞，由进程超时兜底。

界面正文只在观察器内计算哈希，不返回正文。ValuePattern只读取编辑框和Qoder路由，不读取WorkBuddy Document.Value；该属性在原型中曾包含账号数据。密码控件出现时直接拒绝。窗口标题/路径/版本属于用户选窗所需元数据，会进入关联历史。观察器不会继承模型凭证环境。

Qoder 0.4.3.0 实机读取发现：按Document类型直接查询没有得到文档，ControlView缓存树遍历可返回文档和当前聊天UUID。产品采用后者，不把runtime ID当作永久树路径。另以回归测试复现了.NET Framework在核心 `\\?\` 路径下返回无效响应的问题：启动前将路径转换为普通DOS/UNC表示，核对两种表示规范化后的身份相同；原文件锁和内容校验继续保留。

该桥接仍需.NET Framework及系统UIA可用；当前针对Windows x64构建。它不是应用自身工具权限的沙箱，也尚未证明锁屏、不同完整性级别、UIA服务故障、所有长路径/UNC部署等发布环境兼容性。

## 记录与恢复

关联保存在工作台数据目录 `desktop-bindings-v1`，以全部关联字段的摘要为文件名，含项目、名称、观察、确认时间和观察器SHA。原子创建临时记录、同步、非覆盖发布，完整临时记录与正式记录仅在字节一致时按一条读取；不完整、冲突、篡改或缺失项目都保守拒绝。

最多128条关联，当前没有产品内重命名、撤销、归档或专项损坏复核入口。历史关联不能替代计划批准、worker身份、尝试、资源租约和工作流证据。保存关联不新增工作流Assign、Dispatch、Submit、Verify或Accept。

## 后续验收

将经过确认的关联接到桌面执行适配器，补动作前与动作后复核、草稿保护、单一桌面动作租约、持久派发意图、对应轮次的用户回显与回复关联、未知禁止重发、用户取消和原证据恢复。保留用户指定的Qoder验证聊天，WorkBuddy也走既有聊天，不改用新CLI会话代替。

实机版本、模型、窗口/项目切换、同标题多窗口、用户竞争、锁屏、应用退出/升级、长回复与历史裁剪等仍需按原实施方案逐项签收。原型连续20次与本批关联验证，都不能替代完整P4或P6验收。最终本批验证记录见最新交接及证据索引。

## 第037项：独立的固定消息验证

已保存的 Qoder 0.4.3.0 关联 → 准备固定消息 → 再次观察并核对原绑定 → 审阅完整消息和会话UUID → 明确确认一次 → 先保存发送意图 → 桥接发送及轮次回读。准备仅生成核心持有的确认摘要，120秒过期；不接受前端自定义提示词。当前须有2–128个完整可识别历史轮次。任何未核实记录都阻止本数据目录继续发起验证；已通过记录也不能重复确认原摘要。

确认内容绑定项目关联、窗口/进程/版本、Document runtime ID、聊天UUID、内容/布局指纹、历史轮次哈希、固定消息和桥接二进制SHA。每轮哈希由该轮用户消息、助手回复及完成/取消状态组成，历史正文不写入产品记录。成功要求此前历史逐项一致、本次完整提示词回显、助手成功状态和新标记精确一致、输入框清空及无忙碌控件。完整视图要求新增恰好一轮；历史虚拟化后，至少保留两轮先前历史，其哈希须逐项等于原批准历史的完整后缀，再加本次新增轮。证据同时保存原baseline和实际observedBaseline，UI明确显示完整/裁剪及保留轮数，不把裁剪视图当成全量历史。侧栏标记、旧回复、仅保留一轮、缺口或被修改的历史后缀均不能通过。

桥接通过当前登录会话的命名Mutex串行化本产品的输入和回读；这不锁住用户或其他应用的键鼠活动。Windows前台权限由用户确认所在的产品进程传给命名管道认证的核心PID，再传给暂停创建且已经属于专属Job的桥接PID，随后才恢复其线程；没有授权任意PID或ASFW_ANY。权限可能被用户输入撤销，因此动作前仍复核实际前台、窗口身份、输入框焦点、空草稿及修饰键状态。参考微软的[AllowSetForegroundWindow说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-allowsetforegroundwindow)。

Qoder此版本的ValuePattern.SetValue未更新实际输入框，实机表现为草稿仍空、发送按钮禁用，已改为一次固定Unicode文字输入。没有Enter、快捷键或剪贴板操作；读回必须精确等于本次提示词，历史及身份不变且按钮启用，才能Invoke一次。输入不全、焦点竞争、草稿/布局变化和超时均停止，不重输、不补发。唯一Invoke之后，有限重试仅覆盖只读UIA观察；界面更新时ElementNotAvailable/COM读取异常不会导致再次输入或Invoke。检查与OS输入之间仍存在竞争窗口，尚未通过用户键鼠争用、锁屏等完整实机矩阵，不能据此承诺绝对无竞争自动接管。提示词要求不调用工具，但并不构成对Qoder工具权限的技术沙箱。

记录位于desktop-trials-v1。intent与proof分别create_new、同步、非覆盖发布；原始意图不改写。完整pending与相同正式记录可逻辑恢复，半写/冲突/孤立proof/错误摘要均停止继续发送。重开后清空未发送确认，只恢复原验证记录；没有proof的一律待核对，不自动重发。用户可以只读核对原记录，不能靠再次点击发送重放原意图。当前没有专项半写记录复核或手工结束待核对记录入口。旧发送桥接SHA变化时，UI明确说明将采用当前适配器只读复核；请求必须附带当前reader SHA，过期界面拒绝。完成记录由核心另记实际readerSha256，原发送桥接SHA和意图字节不变。此入口只重新读取原消息，不允许恢复发送或采用其他模型/聊天的回复。

本验证不创建工作流Assign/Dispatch/Submit/Verify/Accept，不消耗或伪造项目运行预算，也未接副指挥派发。编程任务的范围/权限/产物、独立验收、自动取消恢复及工作台整体交付仍需后续实施。最终结果以第037项交接和证据索引为准。

## 第038项：桌面会话进入执行配置和方案批准

项目配置现在可选择 Qoder 或 WorkBuddy 的已保存关联。必须属于当前项目并包含模型显示名；旧观察缺少模型时不能直接用于编程配置。选择后分别确认外部应用目录/模型和沿用其自身工具权限，切换应用或关联会清除确认。保存配置不发送消息，也不启动模型请求。真实 WorkBuddy 模型观察尚未实现，因此该分支目前只有合成观察测试覆盖。

`DesktopWorkerSelection` 保存原始完整关联、项目目录、观察到的模型显示名和两项确认。核心验证原记录确实存在、全部字段一致、项目根目录相同，拒绝任意上传或重新计算摘要的伪造关联。主指挥回复只提供任务分解，核心把用户选定的桌面配置原样写入执行方案，并要求明确的 `DesktopSend` 权限。批准弹窗展示聊天、应用/版本、模型、目录、身份证据和权限边界；这些字段进入批准摘要，更改后须重新规划和批准。

分配和回执契约约束会话标识、工作目录、应用及桥接版本，身份证据只能标为 `UiObservation`。Qoder使用观察到的路由UUID；WorkBuddy使用原关联摘要派生的本地关联标识，界面明确没有供应商会话ID。桌面回执不能填写伪造的供应商轮次ID。这里只建立证据约束，没有把本地关联升级为供应商认证。

当前可保存、规划和批准，正式编程任务运行在界面及核心两层明确拒绝，且在申请模型凭证、生成运行记录或副指挥请求前停止。固定文本验证继续独立存在。尚需实现持久派发意图、动作前重新观察、受控任务发送/回读、交付封存、独立验证、取消及未知处置，才能开放持续运行。不能把这次配置链验证当成双应用编程验收。

外部应用沿用自身权限；勾选确认或提示词不能限制它的文件系统、命令和网络能力。费用、实际后台模型调用次数不可精确计量；等待超时也不保证外部任务停止。桌面配置暂不支持金额预算和运行中异常监督。最新检查与实机限制详见最新交接和 `reports/p4-desktop-plan-review-20261010.json`。


## 第039项：受批准任务的持久派发底层

新增 `desktop_execution`，与固定验证记录分开。仅在工作流已存在批准方案和已分配尝试时准备任务，核对原批准的完整会话观察（允许捕获时间更新）、桥接版本、方案摘要、尝试/fence、分配后工作流序列及哈希。任务文本由核心从任务目标、项目目录、交付路径等批准字段生成，附唯一关联标记，不能从用户IPC任意上传。每次计划的派发次数受批准上限约束；该次数不代表外部应用实际后台模型调用量。

保存 `desktop-task-dispatch-v1/<项目和尝试摘要>/intent.json` 后，才以核心身份记录工作流 `DispatchIntent`，之后调用发送器一次。意图和回复使用create_new、同步与非覆盖发布；完整pending允许按原字节读取，截断/冲突/未知文件拒绝。原意图存在或工作流头变化都阻止重发。重开逐条核对方案、批准、分配与派发锚点；记录损坏使宿主进入既有启动诊断路径，暂没有桌面专用人工处置入口。

嵌入桥接新增tasksend/taskread，Qoder 0.4.3.0使用与固定验证共用的前台、焦点、空草稿、模型显示名、窗口/UUID、历史和一次Invoke保护；每次先核对完整提示词摘要。任务回读要求同一模型/聊天、至少两轮原历史的连续后缀、本次完整用户消息、成功状态与回复末尾的新标记。仅保存回复哈希，标记不是验收凭证。首次同步轮询至多50秒，未观察到完成就保留未知；等待结束不会取消外部任务。只读恢复可补写原回复证据，绝不发送或重写原意图；当前要求同一桥接版本。

受信任Rust宿主提供同步 `dispatch_desktop_attempt` / `observe_desktop_attempt`，尚未作为异步产品IPC、界面确认或持续调度入口。发送意图/回读已可使用真实编译桥接，但本批没有调用它向真实应用发送编程任务。正式UI仍保持不可运行。未知任务记录会阻止新的任务发送及固定文本验证；已保存完整回复不自动Submit、Verify或Accept。

补齐调度兼容性：原校验曾要求所有非API/OMP执行带供应商turn ID，与桌面UiObservation冲突。现在仅对原批准桌面选择严格匹配的尝试允许无turn ID；其他接入原条件不变。测试验证Started与重开后的Reconcile(Running)，并确认没有自动提交或验收。

四处中断测试是异常注入，不能称作四次真实强杀：意图发布后、工作流派发后、读到回复后、回复发布后。已验证重开不重发、原意图字节保持、缺少实际派发时不执行回读、错误/裁剪不足回复拒绝、截断/冲突记录拒绝及跨验证发送阻断。原生桥接本批只验证修改后的提示词在窗口访问前被拒绝；没有真实编程往返证据。

下一步必须把此同步底层接为有所有权的后台执行和产品审阅/前台权限传递，再封存原交付文件、提交给独立验证器和主指挥收口。还缺取消/未知人工处置、桥接升级恢复、同批多任务历史连续性、真实WorkBuddy及完整P4故障矩阵。当前准备要求与批准观察保持一致，首任务修改聊天历史后，不能假定后续任务能直接沿用原观察。


## 第040项：一次交付封存、提交与独立验证

`desktop_completion` 已接到受信任同步派发及恢复接口。首次核实并保存回复后，先保存不可覆盖的seal-intent，再读取批准的全部交付文件、复核字节未变化，保存completion。封存包含原review/回复摘要、封存意图摘要、无供应商turn ID的Completed回执及逐文件路径/大小/SHA清单；它是交付哈希封存，不是额外文件备份。独立验证阶段继续使用既有完整项目副本。

原始派发、回复、seal-intent与completion分别保存，最多八个正式/pending文件。读取可接受字节相同的完整pending；截断、冲突或提交后缺少原completion会拒绝打开。历史结构检查不读取当前工作文件，因此后来修改文件不会改写历史，也不妨碍只读展示。

文件只取样一次：新回复在本次调用中可以封存；已有回复而无完整completion时，恢复明确失败，不能重新读取修改后的文件来补成原交付。封存开始后即使只保存了意图、或已取样但尚未落盘，也禁止再次取样。完整completion存在时可恢复提交，但须重新核对当前文件仍与原哈希一致。已经提交的同一记录返回原证据，不重复发事件或重新认定当前文件有效。
