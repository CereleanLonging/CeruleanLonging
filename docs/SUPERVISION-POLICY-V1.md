## 用户流程和约束

需求与计划页增加“记录连续命令失败”选项。默认未启用；勾选后默认阈值 2 次、建议上限 0 条。阈值允许 2–8 次，建议上限允许 0–2 条，0 表示只记录。界面及批准页明确提示当前尚未启用建议调用和发送，填写额度不产生调用。

`ProjectSetupDraft.supervision` 由宿主复制到 `ExecutionPolicy.supervision`，然后作为 PlanRevision 的一部分批准。主指挥只能使用既定配置；不能通过回复提高额度。修改任一阈值或额度都会改变批准摘要，旧摘要不能批准新方案。运行范围门禁仍要求方案 policy 等于保存配置的 policy。

缺失字段表示未启用，使用 serde default + skip-none，不重写旧配置、旧方案或批准摘要。已经批准后不能直接改配置，须沿已有显式修订和重新批准流程。建议仍应计入项目主副指挥累计请求上限；本批只冻结许可上限，尚无建议消费账本，不能宣称已经验证了建议次数恢复或送达预算。

## 异常证据

只统计观察到的命令 `failed`，同一动作摘要且相同退出码连续达到阈值时产生一条异常。同一连续段继续失败不会反复生成；不同命令、退出码或非失败事件会中断计数。文件变更也会中断该连续段。

异常绑定 project/task/attempt/revision、策略、thread/turn 和截至触发序号的观察前缀。ID 与证据摘要由这些内容生成，后续追加观察、重复通知去重、刷新和重启不改变已有异常身份。保存在有限观察投影内；读取时重新计算并验证异常与策略，再核对账本中原方案的策略。伪造异常 ID 或重新计算哈希后擅改策略都会被拒绝。

这些异常只证明“所观察到的同一命令连续失败”，不证明执行者卡循环或没有文件进展。已有遗漏/拒绝标记时，仍可展示已观察事件的异常，必须保留证据不完整提示，不能将其用于自动纠偏。`finished` 仍只表示采集结束；具体建议的有效性还必须核对当前尝试、用户运行授权、取消/暂停、管理预算与最新观察版本。

异常当前是可复现的持久投影，不是建议请求或送达事务。待实现的建议消费次数、状态变更与 Unknown 处置须进入独立追加账本，不得把刷新一次详情等同于创建一次管理调用。

## 采集和构建修复

原生完整观察测试发现，原采集器遇到宿主快照锁竞争时会计为遗漏。已改成容量 128 的脱敏元数据队列：协议线程使用 try_send，读取快照时排空队列。热点协议线程不会等待快照锁或磁盘；队列/记录满时仍准确计数遗漏。原 pending 和最终事件列表也各有 128 上限；这是有限内存，不是无限观察历史。新测试证明锁竞争时的单条事件保留、过载精确计数以及连续通知下取消不饥饿。

另一次原生配置保存失败来自调试桌面自动启动了旧 `cerulean-runtime.exe`。已修正 `scripts/check.ps1` 同步调试核心到同目录 runtime 和 Tauri sidecar，`scripts/desktop.mjs` 为所选 profile 同步 runtime。新增原生测试前置摘要核对；不再把新界面配旧核心的结果算作新版本验收。此修复只证明开发/本机构建配套，不替代 P6 跨版本安装升级协议。
