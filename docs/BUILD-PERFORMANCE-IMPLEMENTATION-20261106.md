# CeruleanLonging 编译性能与资源优化实施方案

文档版本为 1.0，编制日期为 2026 年 11 月 6 日，适用于活动工程 `D:\test\CeruleanLonging-dev`。当前产品基线为 0.1.48，Git HEAD 为 `008674507a4a73723bad59a901d179013f4c1aed`，实施时以包含本地修改的实际源码为准。

本方案面向负责工作台开发、构建和本地交付的执行者。目标是在现有 CPU、内存和磁盘约束下，减少重复编译，缩小界面更新涉及的 Rust 代码范围，并使每次构建的耗时、资源峰值和缓存收益都能核对。

实施顺序为构建测量、缓存复用、开发构建分流、GUI 依赖拆分、按测量结果继续优化核心。Lua 作为未来可编程扩展的独立议题，在明确出现规则脚本需求后评估。

本方案处于待实施状态。跨任务保留构建缓存涉及调整此前的任务结束清零规则，需在启用前形成用户确认的策略记录。文档编写请求对应本方案交付，后续代码实施按届时明确的任务范围推进。

### 导致重复工作的路径

1. 受管入口为每个任务建立独立目录，将 `CARGO_TARGET_DIR` 指向该任务的 `cargo` 子目录。结束时执行缓存清理，后续任务重新生成依赖构建产物。
2. `.cargo/config.toml` 设置了 `incremental = false`。依赖构建缓存复用和 Rust 增量编译分别处理未变化 crate 与变化 crate 内部的重复工作，需分别设计。
3. 桌面直接依赖 `cerulean-core`。GUI 即使复用旁路核心可执行文件，链接 GUI 时也会构建作为库依赖的 core 和 adapters。
4. 核心使用显式 Windows target 和静态 CRT，GUI 使用另一条构建路径，契约导出使用 dev profile。Cargo 会为这些配置生成不同的构建产物。
5. 构建采用单 Cargo 任务、两个逻辑核心、20% CPU 上限和 BelowNormal 优先级。资源保护会增加完成同等编译工作的墙钟时间。

### 实施期间采用的现有约束

| 约束 | 执行要求 |
| --- | --- |
| 构建并发 | 工作区同时运行一个受管构建，Cargo jobs 为 1 |

### 跨任务缓存的建议参数

以下参数用于第二阶段试点，启用前与用户确认。

| 参数 | 初始建议 | 执行含义 |
| --- | --- | --- |

### 基准场景

首次新增构建测量优先附着到下一次计划内交付。P1 启用后，在同一工具链和资源配置下运行一次冷构建、两次同源热构建，并使用两次热构建中较慢的一次验收。

另选三个可独立验证的小改动场景，分别为 TSX 文案或样式、单个核心实现文件、协议类型。执行前保存原文件和摘要，完成测量后通过精确补丁恢复用于测量的改动。每次运行保存 source-before 与 source-after，拒绝将并行发生的其他改动计入同一对照。

## 五 P1 有界缓存复用

### 目录划分

以下为拟实施的目录结构，根目录为活动工程。

```text
.temp/build-cache/
  jobs/<job-id>/
    scratch/
    vite/
    scheduling/
    job-manifest.json
  persistent/<toolchain-id>/<variant-id>/
    cargo/
    cache-manifest.json
target/
  cache-tools/
  debug/
  release/
docs/build-cache/
  scheduling-logs/
  cleanup-logs/
  performance/
```

`jobs` 用于任务临时文件，`persistent` 用于跨任务复用。`target/debug`、`target/release` 和程序包保存经本次成功构建核验的交付候选。构建报告保存到 `performance` 后才进入任务清理。

### 缓存目录身份

工具链身份包含 `rustc -vV` 结果、Cargo 版本及缓存格式版本。变体身份由受管入口确定，至少区分 Windows 静态 CRT 目标与 GUI 所用的 host 路线，以及经过允许的 rustflags。

源码文件摘要、任务时间戳和产品版本用于回执与产物核验。缓存目录身份采用稳定的工具链和构建路线，使源码修改后仍能利用 Cargo 指纹判断哪些产物需要更新。Cargo.lock 记录到输入清单，由 Cargo 的依赖解析和指纹控制具体失效。dev、test、release 与 feature 组合的产物区分继续交由 Cargo 管理。

完整的 Cargo 目录一起保留，包括 `.fingerprint`、`deps`、`build`、需要的增量数据以及配置对应的目标子目录。清理按完整变体处理，避免目录内部的构建指纹与文件失配。

### 生命周期

1. 读取当前策略，完成工程容量与系统资源准入检查。
2. 在缓存管理锁下确定变体，验证路径位于本工程缓存根目录，检查重解析点，取得对应跨进程租约并写入任务清单。
3. 释放短期管理锁，携带租约启动既有资源调度器。工作区构建互斥锁在整个构建期间有效。
4. 子进程使用经清单核验的 Cargo 目录，临时目录仍指向本次任务的 scratch。
5. 等待主进程退出、输出读取完成以及受管子进程收尾，保存结果、timings 和资源回执。
6. 对成功候选执行输入摘要与产物核验，再进入既有交付暂存流程。失败结果保存本次错误及最后成功产物身份。
7. 在租约保护下更新缓存清单，随后释放租约，回收任务临时目录。
8. 根据 TTL、最近使用时间和体积门槛淘汰空闲变体。清理前写入意图，完成后记录实际删除量和未处理问题。

锁的获取顺序在实现中统一定义。清理与构建同时请求同一变体时，活动租约优先。进程崩溃后的恢复依据操作系统文件锁是否仍被持有、任务清单和清理回执判断，避免仅凭 PID 推断归属。

### 失败与恢复

| 情况 | 处理 |
| --- | --- |
| 编译或链接失败 | 保存失败回执，释放任务资源，将本次产物核验状态设为失败，后续显式运行由 Cargo 判断可复用中间结果 |
| 内存保护触发 | 由现有 Job 停止本次进程组，记录峰值和余量，再收尾租约 |
| 缓存清单损坏 | 将该变体标为待处理，保存原因，按可核验路径修复或清理后再使用 |
| 清理遇到占用 | 跳过被占用变体，记录待处理项，下次维护重新核对 |
| 源码在构建期间变化 | 本次候选保持待核验状态，重新确定输入范围后再作交付决定 |
| 回收未完整完成 | 依据清理意图和完成回执恢复，累计删除量只计算已完成操作 |

## 六 P2 开发验证与发行构建分流

### 变更类型与入口

| 变更 | 首选验证 | 交付前追加 |
| --- | --- | --- |
| React、TSX、CSS 和本地前端规则 | `npm run dev`、`npm run typecheck`、相关界面测试 | 最新前端资源对应的 GUI 构建与包核验 |
| Rust 内部实现 | 受管 `cargo check -p <受影响包>`，随后相关测试 | 对应原生程序构建和功能回归 |
| 协议或 domain 类型 | 受管契约导出、TypeScript 检查、协议测试、调用方检查 | GUI 与核心兼容性检查 |
| 验收器或检查器 | 工具自身测试、协议测试、文件摘要绑定核验 | 依赖新工具摘要的宿主构建 |
| 产品版本、CRT、原生依赖或分发配置 | 相应构建与兼容性检查 | 完整交付链与包内身份核验 |

`npm run desktop:dev` 用于需要真实 Tauri 窗口与本机 IPC 的开发验证。开发和 release 各自使用匹配的验收器、检查器及宿主摘要绑定。普通前端预览、合成 IPC 测试和原生运行结果在回执中分别标明。

现有入口与命令可从工程根目录执行，终端需具备 Node.js 22.12.0 或以上版本，以及工程所用的 Rust MSVC 工具链。标准入口通过 `scripts/cache-task.mjs` 检查缓存工具的源码指纹并按需受管自举，可随下一次计划内构建完成准备。

使用 Cargo 命令时，外层由缓存管理器创建会话，再由资源调度器施加限制。以下结构用于一次定向核心检查，前提是缓存工具已通过上述入口完成与当前源码匹配的准备。示例先为当前终端补齐 Cargo 路径，随后检查工具可发现性。

```powershell
$ErrorActionPreference = 'Stop'
Set-Location -LiteralPath 'D:\test\CeruleanLonging-dev'
$ceruleanCargoBin = Join-Path $env:USERPROFILE '.cargo\bin'
$env:PATH = "$ceruleanCargoBin;$env:PATH"
Get-Command node, cargo, rustc -ErrorAction Stop | Out-Null
if (-not (Test-Path -LiteralPath '.\target\cache-tools\cerulean-cache.exe')) {
    throw '请先通过工程标准受管入口准备缓存工具。'
}
& '.\target\cache-tools\cerulean-cache.exe' run 'D:\test\CeruleanLonging-dev' node '.\scripts\build-scheduler.mjs' --rust cargo check -p cerulean-core --locked --offline
if ($LASTEXITCODE -ne 0) {
    throw "受管检查退出，退出码为 $LASTEXITCODE。请核对本次回执。"
}
```

后续若增加脚本别名，统一封装上述受管调用，并为允许的包、命令和参数进行校验。离线命令遇到缺失依赖时，在回执中明确依赖准备状态，再按实际条件处理。

### 增量编译试点

P1 首先测量稳定 Cargo 缓存带来的收益。随后在开发与测试路线试点 `CARGO_INCREMENTAL=1`，通过受管入口在相应子进程环境中显式设置，使其覆盖当前全局关闭配置。发行路线显式采用自身的增量策略，并在回执中记录有效值。

增量试点比较单文件修改后的耗时、进程组内存峰值、增量目录体积与累计淘汰量。开发增量缓存与对应变体共同保留和回收，回收策略必须允许它跨开发任务复用。若单文件改动没有达到收益门槛，或缓存频繁触发淘汰，回退该路线的增量设置，继续保留已验证的依赖缓存复用。

版本交付时执行统一版本同步和原生兼容核验。性能基准中的同源热构建采用相同版本及输入，以使测量能够识别缓存本身的效果。

## 七 P3 GUI 与核心实现解耦

### 拆分目标

建议新增 `cerulean-client` crate，承载桌面使用的命名管道客户端、连接建立、请求响应、事件读取和必要的客户端类型。domain 继续提供共享协议类型。核心持有服务端授权、调度、账本与恢复行为。

```text
cerulean-desktop
  ├─ cerulean-domain
  ├─ cerulean-client
  └─ cerulean-cache

cerulean-core
  ├─ cerulean-domain
  └─ cerulean-adapters
```

GUI 当前使用的 `independent_verifier`、`objective_checker`、`codex_discovery`、`connection_tests` 和 `ipc` 接口逐一建立清单。只把适合客户端的连接与表示逻辑移入轻量模块，涉及文件权限、外部执行或状态变更的操作经现有受认证核心服务执行。若客户端和核心确需共享少量纯函数，按实际依赖提取轻量模块。

## 八 P4 核心与依赖的定向优化

按 timings 中的占比和单文件改动传播范围排序，每轮只选择一个明确的热点。

| 候选方向 | 触发依据 | 实施要求 |
| --- | --- | --- |
| 核心继续拆 crate | core 编译成为热构建主要耗时，且存在稳定的依赖边界 | 优先考虑纯协议或数据表示、存储、平台桥接、应用服务之间的边界，核对依赖环和上层重编范围 |
| 契约导出减负 | `export-contracts` 或 `ts-rs` 宏占有可观耗时 | 评估类型导出 feature，并用生成结果逐字节对比验证结构一致性 |
| Windows API feature 收敛 | windows 相关依赖在 timings 中占比较高 | 根据实际符号清点 feature，逐项验证 Windows 编译和运行路径 |
| 原生桥构建输入 | C# 观察器被频繁重建 | 核对 `build.rs` 的文件与环境重建条件及产物路径 |
| 链接优化 | 链接时间与内存峰值已被采样定位 | 先以现有 MSVC 路线形成基准，再单独评估 linker、codegen 参数及安装兼容性 |
| 大型测试编译单元 | 核心 lib-test 在 3 GiB 下持续无法完成 | 调查测试模块边界与夹具耦合，按覆盖目标拆分可执行测试单元 |

拆分按依赖方向评估收益。修改公共 crate 会影响其依赖方，crate 数量增加也会带来额外构建和维护成本。每次拆分均需给出所减少的重编范围以及新增接口的职责。

对 Lua 的评估单独记录业务动机。适用条件为用户确实需要编写或热更新业务规则，并能明确脚本接口、执行预算、权限和审计模型。现有工作流模板与本地前端规则优先使用现有实现承载需求。

### 性能试点门槛

这些门槛是实施阶段的初始验收目标，结果填入同一基准环境下的实际测量值。

| 指标 | 初始门槛 |
| --- | --- |
| 同源热构建墙钟时间 | 两次热构建中较慢的一次不高于本轮同配置冷构建的 25% |
| 编译复用 | 满足 C1，且报告可追溯到具体产物和阶段 |
| GUI 单点更新 | 满足 C2，并相对改造前同资源限额下的 GUI 更新取得可重复耗时下降 |
| Rust 提交内存 | Job 峰值受 3 GiB 限额约束，每次保存实测值 |
| 系统余量 | 保存运行中最低可用物理与提交空间，保护动作符合现有规则 |
| CPU 约束 | 每次回执读回单任务、两个逻辑核心、20% 和 BelowNormal 设置 |
| 工程容量 | 在计入依赖、缓存、程序包和报告后满足 20 GB 接受上限 |
| 缓存回收 | 空闲缓存触发清理时完成到目标范围的回收，或明确记录活动租约导致的待处理项 |

热构建超过 25% 时，先检查缓存目录是否稳定、环境指纹是否变化、外部构建输入是否每次重写，以及工具摘要是否在触发必要重建。相同输入下重复出现的额外编译作为缺陷处理。CPU 或内存策略的调整另由用户决定。

## 十 分阶段回退

| 阶段 | 回退触发条件 | 回退动作 |
| --- | --- | --- |
| P0 | 计时或日志处理影响正常构建结果 | 回退新增采样接线，保留已保存回执 |
| P1 | 缓存归属、租约、淘汰或结果复用出现错误 | 切回任务独占缓存路线，对空闲持久变体按维护流程清理 |
| P2 | 开发模式、增量试点或新入口行为异常 | 回退对应入口或增量设置，保留已验证的缓存生命周期 |
| P3 | 认证、权限、取消、恢复或封包回归失败 | 回退桌面依赖切换，使用本阶段前已验证客户端路径和可用程序包 |
| P4 | 优化没有收益或引入行为差异 | 回退该项单独的依赖或模块变更 |
| P5 | 新包核验失败 | 继续使用最后一个经过完整核验的可用包，修复后重新形成候选 |

实现回退前先比较当前文件与阶段输入摘要，定位本阶段补丁和期间新增修改。缓存回退通过受管维护操作执行，程序包回退通过既有停止、核验与快捷方式更新流程执行。
