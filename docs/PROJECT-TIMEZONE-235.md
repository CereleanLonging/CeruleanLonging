## 实现范围

新项目可在关联目录时填写 IANA 时区，CLI 使用 `project add --id <ID> --root <目录> --timezone America/New_York`；省略参数时仍是 Asia/Shanghai。项目列表显示已关联的时区。无效名称由核心拒绝，界面保留输入；注册不会自动调用模型。

Project.timezone 沿原配置、方案和批准摘要传入调度与日报。非默认时区使用 chrono-tz 0.10.4 / IANA 2025b 的命名规则，根据接收瞬间计算日期、时间及当时偏移；夏令时回拨不按本地钟面判断账本倒退。分卷文件名包含偏移，卷序号仍保证同日多卷独立。发生日期与接收日期不同时保留迟到标记，跨日索引和 30 新任务 / 256 KiB 默认上限保持。

没有创建第二账本，也没有读取电脑当前时区或使用网络时间服务。

## 兼容边界

- 旧 scheduler 配置 schema 1 保持原字节和固定 UTC+8 投影，包括历史上海夏令时期间的旧输出。默认 Asia/Shanghai 新项目也沿用此规则；不能宣称默认上海已切换为全部历史 IANA 规则。
- 新增非默认时区使用 scheduler 配置 schema 2。旧 0.1.14 的 Host 配置一致性检查和 scheduler schema 检查会拒绝该配置，避免按旧 UTC+8 规则重建。此处是已有旧源码拒绝分支的核对；本轮没有启动旧安装程序或执行二进制降级。
- 工作流事件 schema、全局 reader13 和旧批准内容没有改写。schema 2 是项目 bindings 的版本，不是将全局 reader 提升到 14。
- 时区属于项目不可变身份。相同项目 ID 换时区会拒绝，相同或重叠目录不能通过新 ID 绕过。既有项目不提供就地改时区迁移；必须单独设计包含旧批准、历史分日与归档的显式迁移，不能手改 bindings.json。
- 锁文件新增 chrono-tz、phf 0.12.1、phf_shared 0.12.1；原已有版本未升级。依赖获取最初出现 TLS 握手警告，Cargo 随后成功；没有禁用 TLS 检查。后续编译使用 locked / offline。
- schema 2 规则绑定 IANA 2025b。数据库升级需要独立配置代际与兼容处理；版本断言防止正常测试下静默升级。不能宣称数据库涵盖 2025b 之后所有地区政策变更。
