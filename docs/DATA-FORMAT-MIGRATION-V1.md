## 为什么标记放在事件目录

`events/00000000.json` 是保留的容器声明，包含产品、元数据版本、数据格式、最低读取器代际、原路径、Windows SID、迁移时间及备份摘要。0.1.5 在创建数据目录前、取得原写锁后分别校验格式，加载事件时只跳过这个已经校验的保留文件。未知格式、损坏标记、身份或路径不符均拒绝加载；启动器也先核对格式。

0.1.4 及更早的读取器不认识这个事件结构，会在构建宿主之前报错。因此仅添加一个旧程序会忽略的根目录元数据文件所留下的兼容漏洞被关闭。实机检查直接运行冻结的 0.1.4 存储读取器，确认拒绝且数据文件摘要不变；这不表示旧客户端不能连接由新核心提供的兼容 IPC。

## 使用已有停机与备份流程

先升级到支持目标格式的程序，再从其正常核心审阅并准备升级锁定，备份停止状态的数据。格式迁移与程序更新是两个明确操作；不要在未提交的同格式程序更新事务中间改变数据，原事务会拒绝备份之后的数据变化。

```powershell
cerulean-runtime.exe --workbench --data-dir <原数据目录> upgrade review
cerulean-runtime.exe --workbench --data-dir <原数据目录> upgrade prepare --review-digest <审阅摘要>
cerulean-runtime.exe --workbench --data-dir <原数据目录> upgrade backup --hold-digest <原锁定摘要> --to <新备份目录>
cerulean-runtime.exe --workbench --data-dir <原数据目录> data-format review --from <备份目录> --manifest-digest <备份摘要> --hold-digest <原锁定摘要>
cerulean-runtime.exe --workbench --data-dir <原数据目录> data-format migrate --from <备份目录> --manifest-digest <备份摘要> --hold-digest <原锁定摘要> --review-digest <迁移审阅摘要>
cerulean-runtime.exe --workbench --data-dir <原数据目录> data-format status
```

尖括号必须替换为实际审阅值。审阅和迁移都核对备份完整清单、全部现存数据字节、同一用户和原路径、确切有效锁定。迁移期间持有原写锁、备份和全部原文件句柄；不得用另一目录的备份或已变化的数据继续。

标记先写入唯一 `.format-migration-*.pending` 文件并同步，再以禁止覆盖的同目录改名发布。未完成的临时文件保留并阻止格式加载及新版本解除锁定，不自动清理或重试。发布后标记本身提供迁移结果与备份绑定；输出丢失时先用 `data-format status` 读取现有结果。重复迁移拒绝。

迁移不会解除 hold、启动核心或恢复项目。确认结果后才明确执行原 `upgrade release --hold-digest <原摘要>`，再手动启动核心。解除锁定也会核对数据格式，遇到残缺或不支持的标记保持锁定。

## 数据恢复与程序兼容

需要退回旧格式时，先停止核心并保留完整的迁移后目录，再使用原冷备份恢复到原用户的原路径；目标必须不存在。恢复包含原锁定，明确解除后才运行旧程序。工具不覆盖现有目录，也不删除迁移后的证据。真实检查验证恢复后的所有文件与备份完全一致，原批准与项目保持，旧读取器恢复可用。

程序包能力新增 `dataFormatGuardSchema` 和 `readableDataSchemas`，与真实 `--build-info` 一并核对；清单伪称兼容而程序不支持会被拒绝。`dataSchema: 1` 表示默认新目录格式，不代表已有目录一定是格式 1。

更新工具检测到格式标记后，要求候选程序能实际检查该格式，并要求源/候选都支持它，避免提交前回滚时旧程序打不开数据。准备以及后续变更重新核对，未完成迁移阻止程序更新。对已变化的数据，原事务的完整备份比对依然有效。

## 验收范围

本批证明的是容器 1→2 的明确迁移与旧读取器门槛、原位置备份恢复。真实迁移保留了批准事件和项目；未知版本、错误审阅、数据变化、活动写锁及重复迁移拒绝。部分发布检查使用受控残缺文件，不能代替实际断电、磁盘满或进程终止矩阵。

上述102残缺文件检查由103进一步补充：测试构建分别在创建前、空临时文件创建后、临时文件同步后、标记改名发布后停住，父进程核对回执PID及令牌，确认原写锁仍由该子进程持有，然后通过原进程句柄终止并等待退出。每次均保持原事件与hold，保留整个中断目录，再从原备份恢复到原位置；旧版重新读取原批准计划通过。空/已同步临时文件阻止新版状态读取、解锁和重复迁移；已发布标记可以只读核实结果。

冻结0.1.5程序的额外检查以填满的输出管道阻止迁移结果返回。父进程在该原进程仍活着时读回有效格式2及备份摘要，然后终止原进程并确认没有收到任何迁移ACK字节。再次读取结果一致，重复迁移拒绝且不改文件，原hold明确解除后计划可正常读取。此场景证明程序进程在结果返回前退出可恢复，不证明磁盘控制器缓存、物理断电或磁盘耗尽下的持久性。

0.1.6已把上述CLI接入独立数据维护窗口，从原维护窗口的“打开数据迁移与恢复”进入。界面提供备份、审阅、迁移、核对、原位置恢复和明确解锁；尚非程序和数据的统一迁移事务，也未完成跨用户/路径/机器迁移。恢复前保留完整原目录目前仍需另行操作，界面不会覆盖现存目录。格式 2 程序更新兼容矩阵包含真实核心读取和受控源/候选能力组合；不把同一个新版本的能力检查说成两个格式 2 版本之间已做真实程序替换。
