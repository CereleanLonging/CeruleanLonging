# 212 管理来源接入启动、监督与收口读取

2026-10-20。承接210外部Codex主指挥与211DeepSeek副指挥账本。本批处理执行链中的OpenAI专用读取假设；不改变用户批准，不发起真实模型调用，不启用未接好的来源配置。

## 问题与结果

原启动证明会对项目中已有响应头的每一条管理记录读取 `DecisionObservation`。这个类型只描述OpenAI回执，所以已有外部Codex方案，或DeepSeek分配后的重开，都会被当作缺少OpenAI回复。分配桥、并行运行、监督投送/视图及共享收口也有同类假设。

现在管理账本提供按真实来源读取的原始决策。OpenAI保留原回执；外部Codex保留会话绑定、原请求和回填；DeepSeek保留自身请求、回复及用量。没有给其他来源伪造OpenAI响应ID、用量或费用归属。

新启动证明的来源字段只在非OpenAI记录中出现，旧证明的序列化字段与原OpenAI观察摘要保持不变。监督引用使用各自原回复的摘要；旧OpenAI监督记录仍按原DecisionObservation计算，已有建议不因新读取器而失效。

## 保留的授权和恢复约束

- 实际派发、应用和用户批准仍走原入口，继续检查当前状态摘要、原配置、用途、响应链、执行者、尝试、租约以及记录复核状态。
- 历史读取允许读取已明确复核的有效原回复，用于恢复和关闭已有启动；历史读取不授权重新派发。首轮回归发现把派发门槛放到原证据读取里会阻断旧OMP复核恢复，已将两者分开，保留该失败证据。
- 错误执行者或没有有效分配决定的回复，不能作为启动证明；重开不会补发模型请求或启动执行者。
- 来源读取层不决定供应商调用路由。主/副指挥配置、运行器发起新请求、外部chief最终Accept及前端仍需按下面顺序接线。
