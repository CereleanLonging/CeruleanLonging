# 307 后台派生缓冲与索引证明容量预算

继承 302–306 的事件权威、异步投影、共享执行池及当前用户保护的检查点。此次补 128 个账本队列仍可能同时持有大量完整克隆的问题，不重发旧任务，不改变事件 schema、reader generation 或 SQLite schema。

## 当前实现

- 进程共享最多 128 MiB 的**保留序列化缓冲容量与索引读取证明容量**预算；仍最多两个后台执行线程、128 个处理中账本链。
- 普通索引和日报/state 快照各最多 16 MiB，检查点最多 32 MiB。编码每次扩容前申请容量，失败即结束编码并释放已持有容量；按实际 Vec capacity 记账，不按字符串字符数估算。
- Store 的计划/事件、工作流状态、日报文本、检查点历史使用借用序列化，排队期间保留有界字节，避免排队对象持有完整状态克隆。工作流的索引行构造仍在主线程，但不再复制整份日报给索引和文档队列。
- 更新时先释放已被替代的 pending 索引/文档及旧 receipt；原 pending 检查点继续保留，防止新索引覆盖未发布检查点。正在执行的旧工作仍由自身持有，不强行取消。
- SQLite 读取证明按结构、Vec capacity 与 String capacity 申请同一预算；返回给读者的 Arc 保留预算租约，直到最后读者释放。队列拒绝、panic、替换和正常退出会释放各自拥有的缓冲。
- 后台索引/文档依次解码并处理；检查点直接给来自可信宿主的已序列化内容增加保护 envelope，不再解码后重建整份历史。Envelope、原始事件 proof 与当前权限验证的 306 规则不变。
- 索引整体 fingerprint 改为流式 SHA256，避免为了摘要再分配完整 JSON 字符串；摘要与原序列化字节一致。

预算不足不撤销已提交事件、不重新发送模型任务，也不改变批准/资源/验收。索引不可用时仍从权威内存读取；显式刷新或以后重开可在容量释放后重建。失败通过现有派生诊断显示。检查点、索引和文档仍分别处理失败。

## 不能扩大解释的边界

128 MiB 是上述保留数据的容量账本，**不是整个进程 RSS 上限**。分配器元数据、控制对象、解码时的临时对象、SQLite 本身及查询结果、主线程索引行构造、日报预渲染、常驻权威历史均不在此总预算内；可能短时同时存在编码与解码对象。旧读取证明在构造后才计入保留预算，失败会丢弃，不声称整个构造过程已先行预留。

仍应继续约束可编辑 SQLite 缓存的读取长度/累计结果，减少主线程 O(n) 工作并评估更大账本。不能把本轮通过写成全部内存/性能或正式验收完成。序列化也会增加调用线程 CPU 工作；本轮并未证明用户任务提速。
