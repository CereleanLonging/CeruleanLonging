## 支持的更新范围

本版为同数据格式的双程序更新：替换 `CeruleanLonging.exe` 和 `cerulean-runtime.exe`，保留原卸载程序、资源与其他普通文件，更新当前用户安装登记中的 DisplayVersion。不是执行新 NSIS 的通用安装迁移。候选必须声明 `binaryUpdateSchema=1`、`dataSchema=1`；源 0.1.1 被明确列为原格式基线，后续源版本也须声明同一数据格式。候选版本必须严格前进，不能把同版本重装或降级当作升级。

0.1.2 核心增加上述能力声明，备份读取明确接受 schema1 writer 0.1.0/0.1.1/0.1.2。工作区版本、Tauri 与 npm 版本一致，依赖版本未升级。活动账本格式没有变化；能力声明不代替尚待实现的数据目录版本门槛与迁移事务。

维护需要原安装包和候选包的已审阅清单摘要、原安装位置、数据目录以及已准备的 hold 摘要。原实际程序必须匹配源包；hold 必须来自同一源核心的实际摘要。只支持同用户 NSIS 登记，安装目录、事务目录、数据目录及两包目录互不重叠，事务与安装在同一卷。当前目录清单最多 4096 项、2 GiB；普通文件/目录之外的重解析点和硬链接拒绝。

源包与候选包经过实际签名/摘要/能力检查，并在整个动作中持有原文件及目录句柄。内部未签名包必须明确选择内部通道；正式发布签名成功路径仍待证书和验收。包摘要是字节身份，不是发布者身份。

## 操作与持久记录

| 动作 | 作用与结果 |
| --- | --- |
| Prepare | 核对安装归属及 hold，创建独立事务目录、intent、原绑定数据备份和 staged-program；核对新文件与候选摘要、其余文件与原程序清单。返回必须审阅的 planDigest，状态 prepared。 |
| Review | 校验计划摘要、SID、事件摘要链和状态转换，只读列出日志状态及 installed/previous/staged/failed 目录属于源版、候选版、缺失、改变或不可读。不会启动程序或自动修复。 |
| Apply | 只允许 prepared 一次。重新审查两包、备份与原数据；写入 apply-intent，将原目录移到 previous-program，再将暂存目录发布到原位置，核验并更新登记，状态 installed-held。 |
| Rollback | 明确调用、提交前可用。校验原保留程序与当前程序，候选移到 failed-program，原目录恢复到原位置，恢复 DisplayVersion。数据保持 hold，不重新运行项目。 |
| Commit | 仅允许 installed-held，核对程序/数据/登记后写带 in-process-v1 标识的 commit-intent；保持原写锁，在同一维护进程中将原 hold 禁止覆盖地归档，记录 committed。不会启动核心。 |
| Reconcile | 仅处理未决 commit-intent；从原备份基线识别本次新增的唯一、完整匹配的释放归档，确认当前候选程序与登记，追加 committed。只写事务记录，不再解除锁定、不修改项目数据。 |
| AbandonCommit | 仅处理 in-process-v1 的未决提交；确认原 hold 保持、没有本次释放凭据、数据仍匹配备份，追加 commit-abandoned。之后只能明确 Rollback，不允许重发 Commit。 |

后续动作必须传入 Prepare 返回的 `-PlanDigest`；修改计划、丢失/篡改事件、非法状态转换都会拒绝。记录采用唯一临时文件、写入并 Flush、禁止覆盖的原名发布；进程中断留下的临时文件保留，不作为完整事件读取。持久数据不包含 Key 或模型私有推理。

典型后续操作（尖括号须替换为已审阅值）：

```powershell
powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File D:\test\CeruleanLonging\scripts\manage-windows-update.ps1 `
  -Action Review -TransactionDirectory <原事务目录> -PlanDigest <原计划摘要>
```

Apply、Rollback、Commit、Reconcile、AbandonCommit 都必须采用 Prepare 时相同的内部/发布者策略。没有默认“使用最新包”、自动重试或自动解除锁定。提交后该事务不允许降级；需新的兼容审查，不能恢复旧程序后让它直接读取可能已变化的数据。

数据 writer.lock 在检查与程序替换期间独占持有，必须是原普通零字节文件；准备、替换、提交或回滚前重新验证备份及活跃数据全部字节。提交结果对账只确认已发生的释放，不要求释放后数据仍等于提交前备份，避免将用户之后正常使用误判为提交失败。安装归属按锁定 NSIS 模板核对：产品默认路径不带引号，InstallLocation/UninstallString 带引号；只更改本次安装的 DisplayVersion，不重写其他登记。

## 中断与并发

Windows 实验确认：即使子文件句柄共享 DELETE，打开的子文件仍会阻止父目录改名。因此只在单次改名前关闭本工具的程序检查句柄，改名后立即重新取得并核对。并发用户启动可能使改名或重新取得句柄失败；保留日志和目录，不杀用户进程、不自动重复 Apply。不能声称整个改名窗口完全排除外部启动。

原目录移走后、候选发布前，安装路径会短暂不存在。持久 apply-intent 已在此前发布；明确 Rollback 可恢复原目录。候选发布后仍保持数据 hold，用户无法通过正常核心启动进入项目执行。若检测到不能解释的目录内容，工具拒绝覆盖，保留现场供审阅。

## 提交中断的对账

098 用独立核心子进程 release。若维护进程退出，子进程可能继续运行，所以“此刻 hold 还在”不足以证明释放不会发生。099 将释放归档留在维护进程内，整个过程继续持有原 writer.lock。原 hold 已在 Prepare 时由核心核验，在每次变更前核对原摘要与全部数据；归档保持原字节，使用原 history 命名格式与禁止覆盖的同卷改名。正常 CLI 的原 release 命令没有改动。

`Review` 对未决提交尝试取得原数据写锁，再返回 releaseObservation；若核心仍活动或证据无法读取，只报告 unavailable，不关闭核心、不猜测结果。

| 结果 | 证据与可用动作 |
| --- | --- |
| released | 原 hold 已不存在，本次备份基线之后恰有一份命名及字节摘要都匹配的原 hold 归档；可明确 Reconcile。 |
| still-held | 原 hold 摘要保持，没有本次匹配归档；新 in-process-v1 提交可明确 AbandonCommit，然后 Rollback。 |
| conflict | hold 改变、原 hold 与新增归档同时存在、匹配归档重复或归档被改动；保留现场，拒绝自动收口。 |
| unproven | hold 缺失但没有唯一新凭据，或只有备份基线中已有的旧归档；不能推断成功。 |
| unavailable | 原数据写锁或证据不可读；先解决具体占用/读取问题。 |

Reconcile 再核对源/候选包、备份、当前候选程序与安装登记，持有事务锁和数据写锁后才追加结果。不会运行 release、不会重新启动项目。重复收口被拒绝，原记录保留。若中断仅留下新建的空 `upgrade-holds` 目录，明确放弃与后续回滚允许这一固定空目录差异；任何新文件仍阻止按旧数据回滚。

旧 098 未带 releaseMode 的提交记录，如果已有唯一新归档，也可对账成功；**仅有旧原 hold 时仍拒绝 AbandonCommit**，因为旧释放子进程的生命周期没有记录，不能证明不会继续动作。此类现场需要专门人工审阅，不能删日志或假定没有进程后重试。旧工具尚未发布给用户，本批保留该限制，不伪称所有旧故障状态已自动恢复。
