# 251 显式 API 任务交付文件写入范围

## 行为与接线

新增可选`ApiWorkerSelection.writeScope = "declared-artifacts"`。省略时保留原工作区写入行为和旧序列化字节；开启后，当前任务最终批准的artifact_paths成为原生API文件工具的准确路径白名单。模型选择、任务清单和范围均进入原批准摘要及ApiRunIdentity，不允许用旧批准放宽或切换范围。无write-files能力时不能设置写入范围。

ApiFileTools由已验证的原身份和原方案取当前任务的清单；共用文件引擎在创建目录、生成写入镜像或打开写目标之前拒绝未列明路径。要求使用清单中的准确拼写，不将不同大小写、短名、路径前缀或流别名推断成授权。模型工具schema也列出可写路径，但真正约束在核心执行端。ReadFiles仍可读取工作区依赖；原遍历、重解析点、硬链接、受保护路径、摘要冲突等检查继续执行。OMP和原人工修复入口使用原范围语义，本轮不替它们新增权限。

UI的API配置支持选择“仅当前任务的交付文件”；方案审阅显示选定范围，现有ExecutionAuthorization同时显示具体交付文件。只读切换清除写入范围。默认配置和执行配置档案复用同一组件。类型由Rust重新生成，contracts仅新增范围类型和可选字段，没有覆盖其他合同改动。

245材料工具允许这个可选值，拒绝未知/null/对象形式；旧配置继续有效。250团队绑定沿用完整worker内容摘要，所以新范围也绑定到实际setup/批准方案。基线与团队后续对照须冻结相同worker配置，不改写旧材料包或把旧250结果改标为受限范围。

## 实际检查与失败保留

共5个去重Rust测试通过：范围/批准/旧字节、真实工具路径与硬链接、旧API工作区行为、旧OMP实际写入，以及新隔离P01团队。4个UI功能场景、TypeScript、fmt和core/domain全目标严格Clippy通过。

新P01先读取真实文件摘要，再发出跨分支写入请求；三个请求都以范围错误拒绝。随后同一原任务完成合法工作，共14条合成执行者响应、7条管理操作、3次独立验收，三任务全部Accepted，两次重开0重派。原始写入镜像逐项确认只有left.mjs、right.mjs、main.mjs各一次合法写入；拒绝的请求没有创建写入镜像。模型响应均为合成，无用户Key、真实模型或桌面操作，临时无效测试凭证已清理。它不计入72次真实实验。
