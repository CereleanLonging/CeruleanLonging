# 224 DeepSeek 副指挥运行期间的凭证保护

2026-10-20。此次从首批供应商验收检查发现并修复一项并发缺口，不重做 218 真实三级闭环，也不复用其一次性 Key。

## 问题与影响

`set_openai_key` 原本会拒绝指挥请求进行中的凭证变更。DeepSeek 新增副指挥后，`set_provider_key` 仍只通过原执行者、OMP 和模型列表请求检查，没有检查正在运行的副指挥请求。

副指挥在派发前已将 Key 放入本次客户端。因此，原入口可能在请求仍运行时删除或替换凭证存储，使界面连接状态与原请求实际持有的凭证发生分离。删除本机 Key 本身不会撤销已经发出的供应商请求。另一个不对称点是：启动副指挥会拒绝正在运行的连接检查，启动连接检查却没有拒绝正在运行的副指挥。

两个本地受控用例在修复前实际失败，分别证明凭证删除/替换未被拦截、连接检查可以启动。原失败日志保留于 `reports/deepseek-credential-interlock-224/reproduce.*`。用例只使用临时目录和无效合成值；连接检查的旧实现复现使用损坏的本地加密包，读取凭证即失败，不向供应商发送。

## 修复

`provider_connections.rs` 从活动指挥请求的原记录读取供应商身份，属于 DeepSeek 时拒绝变更 DeepSeek 凭证或启动其连接检查。缺失或无法核验原记录也不放行。它不根据模型名字推断供应商，不添加新的持久状态或改写旧记录。

运行中的请求、原回执和计费观察保持原流程；请求结束后正常轮询清除活动项，即可删除或替换本机 Key。无关供应商的编辑不受此检查影响；已有 OpenAI 保护不变。
