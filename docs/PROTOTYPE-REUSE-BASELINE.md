## 继承边界

原型已经证明指定版本和配置下的接入可行性、连续短文本任务及记录中相应的取消/恢复行为。旧结论继续有效，不能因为产品阶段另有缺口而改写成“从未接通”。具体取消/恢复范围按原报告核对，不由连续回复记录代证。

原型 WorkBuddy 为 5.7.6，当前产品原生适配为 5.7.7.0。原驱动限定测试聊天、短文本消息和特定历史锚点；迁移应复用已验证的行为，消除测试专用假设并对接产品的批准/持久派发/产物验收。原型通过不等于新版产品的实际编程、打包升级和 P6 已通过。

## 后续执行规则

- 排错顺序：预案与验收报告 → 对应原型实现 → 当前实现差异 → 最小必要修复/验证。
- 每次补测写明改变了什么、复用了什么、还缺哪项证据；未改变的能力引用旧记录，不重做整套基础接入。
- 优先补产品调度、编程交付与独立验收；受控模拟验证应明确标注，不能代替真实模型或真实桌面验收。
- 实机动作继续沿用用户具体授权与失败停止约定；历史成功不能自动授权失败后的重发。
- 保存动作/决策摘要及证据，不保存私有推理、凭证或无关聊天内容。旧冻结报告和索引不修改。

## 本次对照结论

旧驱动已使用 focus-click；产品先尝试 SetFocus 后再次修复焦点属于可避免的重复排查。旧版发送使用 Invoke，新版实测出现草稿未提交后改为真实点击，属于有实际差异证据的适配，不能一概算作重复工作。

产品现有通用持久调度可以承载 WorkBuddy 本地关联，无需新写另一套调度器。补齐版本路由和本地回复凭据后，应复用现有批准、一次性派发、未知结果回读、产物封存、独立 Node 检查、主指挥验收及连续任务流程。新版真实发送、丰富代码/工具回复、真实编程仍按独立证据标注。
