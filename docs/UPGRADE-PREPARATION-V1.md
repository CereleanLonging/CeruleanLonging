# 升级前状态审阅、锁定与备份

097 更新：0.1.1 内部安装包已包含以下能力，并增加候选包审查及明确的备份读取版本列表，见[更新包审查说明](UPDATE-CANDIDATE-V1.md)。实际安装升级事务、活动数据格式迁移与程序回滚仍待完成。下文保留 096 原验收范围；其中“仅开发构建”的时点现已推进到 0.1.1 release。

096 在原工作台 CLI、单写核心和冷备份上增加升级准备流程。先明确暂停后续派发并处置未决任务，再审阅核心；准备成功会写入持久锁定记录并退出原核心。后续窗口不能把本版本核心重新启动，直至用户明确解除锁定。

本批是开发构建的新增能力，095 已冻结的 release 安装包保持原样，**不包含这一流程，也不会识别新锁定文件**。不能将旧二进制对新锁定状态的行为当作本次保护范围。后续升级执行器必须核对待安装版本对锁定记录的支持；跨版本兼容与旧程序拒绝不兼容数据仍为 P6 未完成门槛。

## 操作顺序

以下使用包含本功能的新核心，数据目录应取实际工作台配置。尖括号需要替换为审阅结果，命令不自动选取摘要。

```powershell
cerulean-runtime.exe --workbench --data-dir <数据目录> upgrade review
cerulean-runtime.exe --workbench --data-dir <数据目录> upgrade prepare --review-digest <review.digest>
cerulean-runtime.exe --workbench --data-dir <数据目录> upgrade status
cerulean-runtime.exe --workbench --data-dir <数据目录> upgrade backup --hold-digest <holdDigest> --to <不存在的备份目录>
```

`review` 返回原完整快照和 `upgradeReview`，其中包括阻塞项、快照摘要、核心版本、实际运行二进制 SHA256 和进程身份。它读取运行中核心，不能自动关闭任务或替用户处置 Unknown。准备使用同一锁下重新核对的状态摘要，过期摘要或阻塞项均拒绝。

准备门槛比普通退出更严格：原 `can_shutdown` 检查通过之外，还要求没有核心/API/OMP 诊断、管理或启动发布问题、启动保留项，以及未解决的指挥记录。指挥检查使用全历史项目计数，不只检查第一页；桌面检查同时覆盖未完成的试验回执和待处理的任务记录。诊断模式可以允许普通退出，但不能据此允许升级准备。

`prepare` 成功后返回 `upgradeHold`，CLI 使用事先保留的原核心进程句柄等待其退出。通信或等待失败时不重发、不启动替代进程；先用离线 `upgrade status` 核对已有记录。收到 ACK 不等于任意外部任务已经完成，是否允许准备仍由前述门槛判断。

`upgrade backup` 沿用 [冷备份](COLD-BACKUP-V1.md)的完整清单、哈希及普通文件约束。在持有源数据根写锁和全部文件句柄期间，核对原锁定记录的确切摘要，拒绝缺失、错误、残缺或被替换的记录。它把锁定记录也备份进去，恢复备份不会顺便解除升级锁定。

## 中止准备与恢复数据

若决定取消准备，或新版本检查完成、准备恢复使用，必须先审阅当前记录，再执行：

```powershell
cerulean-runtime.exe --workbench --data-dir <数据目录> upgrade release --hold-digest <当前记录摘要>
```

解除只在原写锁可独占取得、摘要仍匹配时进行。原记录通过禁止覆盖的改名保存到 `upgrade-holds`，不会删除证据；命令不启动核心、不恢复项目运行。之后用户可以显式 `service start` 并继续原方案审阅和恢复流程。**解除锁定不是新版本验收通过的证明。**

若维护期间数据损坏，先保留失败目录，再按冷备份规则将备份恢复到原用户的原数据路径。目标必须不存在，工具不替用户覆盖或删除失败数据。恢复后仍有原升级锁定，需再次审阅并明确解除。实际本机测试保留了故障数据目录，恢复全部字节并验证原项目不变；并未更换应用版本，不能代证跨版本程序回滚。

持久记录写入失败可能留下残缺文件，本版本仍拒绝启动，不会当作“没有升级”。`upgrade status` 对有界普通文件返回原始字节摘要与 `validRecord: false`，不会回显任意文件正文。用户明确提供该摘要可将残缺记录归档解除；它不能用于 `upgrade backup` 的已验证准备流程。此能力针对部分写入的人工审阅恢复，不声称物理断电完整保证。

## 退出屏障与证据

原 IPC 在确认退出和返回快照之间分别加锁，已连接的请求可能在退出检查之后继续执行。现统一使用 `ServiceState`：在同一互斥锁内完成检查、快照和停止标记；停止后所有排队请求返回 `coreStopping`，计时轮询也不再驱动任务。退出信号在等待响应写入前发出，因此丢失 ACK 不会留下继续接受命令的核心。

原普通退出、诊断重启和已审阅停止重启都使用这一屏障；协议版本、SID/ACL、请求上限及原任务权限未放宽。未包含新增字段的普通 `ServiceReply` 保持原序列化结构；新审阅数据只用于新的升级操作。
