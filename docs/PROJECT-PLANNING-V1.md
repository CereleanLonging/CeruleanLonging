# 项目需求配置与主指挥规划入口

2026-10-08。原生“需求与计划”页新增项目规划表单；配置、请求和方案应用走常驻 Rust 核心。配置及原生操作验收通过，尚未配置真实官方 API Key，因此真实主指挥生成与完整 P2 尚未验收。

## 用户流程

1. 在项目设置关联现有项目目录，并登记实际独立验收程序及固定依赖文件。
2. 在“向主指挥提交需求”选择项目，填写需求、主/副指挥模型、Codex 程序和编程模型、验收工具及逐行参数、产物相对路径、编程请求上限、项目主副指挥累计请求上限和执行时限。
3. 保存只读取并固定程序摘要，不发起模型请求、不修改项目、不授予执行批准。配置版本及摘要进入独立记录，重开恢复。
4. 本机配置官方 Key 后，可请求主指挥生成方案。一次明确点击只建立一个持久化请求；重复/未知请求仍按原约束拒绝重发。请求可能产生供应商费用。
5. 有效 Plan 回复由核心转换成完整执行修订，出现在“项目执行方案”；用户使用现有完整授权对话框审阅和批准。模型不能代替这一批准。

本批没有在批准后自动派发。副指挥、worker 和验收链的组件已经实现，下一步是将它们串成用户明确启动且可暂停的持续项目执行流程；不能把当前“批准”按钮解释成已经完成自动调度。

## 约束与记录

`ProjectSetupDraft` 只接受合法模型 ID、普通产物相对路径、有限参数数量与长度、1–1000 次请求上限以及 10–3600 秒时限。执行配置当前固定 Codex 编程路线，真实程序和模型可用性仍在连接/派发时验证，保存本身不证明程序能运行。

保存后的 `ProjectSetup` 固定实际 worker 的程序 SHA-256、验收工具、参数、产物、执行权限、快照规则及主副指挥配置。快照暂固定排除 .git/node_modules/target、最多 10000 文件/64 MiB；产物不能处于排除项。验收超时取执行时限和 300 秒的较小值。这些内容仍在最终方案中展示并批准。

`project-setups/<项目>.<版本>.json` 采用不覆盖版本文件、摘要校验、同目录临时文件写入/sync/rename；重开核对项目和验收登记、连续版本及摘要。每项目最多 32 个配置版本、目录最多 256 条、单条 64 KiB。残留临时文件或损坏记录当前拒绝打开，恢复处置待完善。已有活动/待处置指挥请求、正在执行的任务或已批准待执行任务时禁止修改配置。

配置摘要与内容进入主指挥上下文和当前状态摘要。请求由窄 IPC `RequestChiefPlan(projectId, setupDigest)` 发起，用户不能指定任意模型角色、命令或响应。核心按保存的主指挥模型与需求构造请求。预算按项目所有已记录的主副指挥请求累计；修改配置不会清零，但用户可明确保存更高的新上限。未知或失败请求仍占一次记录。请求次数不是金额预算，本版不声称可限制 API 金额。

有效回复只能选择配置的 worker-codex 和对应验收登记；任务数量不能超过编程请求容量。核心把每项任务绑定到保存的完整范围与验收检查，再经现有 PlanRevision 校验和管理应用事务提交。当前所有任务共用一套产物和检查，适合一个整体编程交付或每阶段都满足该检查的任务；多阶段不同验收范围和多执行者配置仍待扩展，不能据此宣称复杂项目拆分已经完整。

Wait 会保留原响应并本地消费，界面显示补充信息，不产生工作流事件。规划返回无效/不匹配方案时不会产生批准或派发，保留记录和错误。原始响应可重开核对；目前 Wait 的用户提示是内存投影，重开后提示尚未重建，待完善。Unknown、未应用结果的用户处置/重新规划也仍需实现。
