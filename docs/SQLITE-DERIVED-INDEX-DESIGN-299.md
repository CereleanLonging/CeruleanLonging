# 299 派生 SQLite 索引：实施边界与离线依赖核查

状态：**设计已核对，生产实现未开始，P1/正式验收仍未通过。**本文件不改变 297 内部候选、现有账本或旧报告。`docs/IMPLEMENTATION-PLAN.md` 第 6 节要求 `index.sqlite` 是查询缓存，事件 JSON 是唯一权威；2026-10-07 的 P1 验收也把索引列为缺口。后续范围文件未取消该项。

## 当前代码接点

产品存在两种独立的单写账本，不能只给其中一种加一个空数据库文件：

| 账本 | 目录与提交 | 应缓存的查询字段 |
| --- | --- | --- |
| `crates/core/src/lib.rs::Store` | 产品数据根的 `events/00000001.json`；`Store::open` 全量验序与重放，`append` 在事件发布后更新内存 | 计划 ID、批准状态、事件序号/类型/时间 |
| `crates/core/src/scheduler.rs::DurableWorkflow` | 各工作流目录的 `events/<序号>_<operationId>.json`；`open/load` 全量验序与重放，`command_observed` 在发布事件后投影 `daily/` 与 `state.json` | 事件序号/哈希/operationId/任务/尝试、任务现态、跨日未完成任务、日报卷路径 |

每个账本在**自己的根目录**保存 `index.sqlite`，不要共享文件或把缓存作为第二权威。现有 `inspect_existing` 明确只读，不能被索引重建悄悄变成写操作。`backup::inventory` 会按字节纳入新增文件，因此新索引会影响备份清单和恢复对照；恢复后应先校验原事件，再核对/重建索引。旧读者即使继续写事件，新读者也必须通过链头比较发现并修复落后索引。

## 推荐实现

1. 为 `cerulean-core` 锁定 `rusqlite` 与 `libsqlite3-sys`，优先用 `bundled` 以固定 SQLite 版本、免依赖用户机器的 DLL。版本与新增传递依赖应在获取后写入 `Cargo.lock`，核对许可证、MSVC 构建及发行载荷；不引入手写 SQLite FFI，也不让 Node/Python 成为 Rust 核心的运行时数据库驱动。
2. 在新模块中封装连接、schema、链头检查、重建及只读查询。`meta` 至少保存 schema 版本、账本类型、事件数量、最后哈希及绑定摘要（工作流）；`events` 以序号为主键，保存 operationId、时间、哈希、任务/尝试等可查询列；工作流另有 `tasks` 当前状态与 `daily_volumes`，基础 Store 另有 `plans`。字符串列采用参数绑定；不存凭证或模型私有推理。
3. 仍由 JSON 事件**先**验序、验哈希、重放领域规则。首次启动、缺失、损坏、schema 不符或链头不符时，用已验证的内存结果在同目录临时 SQLite 文件中构建，事务提交并关闭连接后原子替换 `index.sqlite`。必须拒绝链接、junction、目录伪装和非普通文件；数据库自带 journal/WAL 残留应先由 SQLite 恢复并关闭，不能当作权威事件，也不能无条件删除未知文件。
4. 正常命令的顺序保持为**事件发布成功 → 更新内存/原投影 → 更新派生索引**。索引写入失败只令索引不可用并报告诊断，不得撤销已发布事件、重新派发意图或重试模型调用；下一次可靠重开从事件重建。若保持现有 `state.json`/日报故障后实例须重开的规则，索引处理不能放松该规则。任何索引读取都先核对链头；不匹配时退回已验证内存/事件数据，不返回过期结果。
5. 采用短事务和非 WAL 模式以避免冷备份时残留 `-wal`/`-shm` 文件；备份/恢复、格式升级和旧读者回读都要按新增文件重新验。索引不是授权事件，不能单独用于判断是否发送、验收或释放资源。

## 最小差异验收

新增隔离测试分别覆盖两种账本：空库生成、事件/任务/计划查询与内存一致；删除或损坏索引后重建且事件字节不变；索引链头落后/伪造超前时重建；事件已发布但索引被真实文件锁阻断后，重开仍只保留一次派发意图并恢复 Unknown；链接/目录路径拒绝访问且不跟随；冷备份/原位恢复后索引与账本一致；旧读者新写事件后的新读者补建。工作流还需核对跨日未完成任务与日报卷查询。精确测试、格式及严格 Clippy 通过后再做发行/安装矩阵，不能仅凭 SQLite 文件存在标 P1 通过。
